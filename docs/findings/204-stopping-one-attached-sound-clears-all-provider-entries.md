# Finding 204 — Stopping One Attached Sound Clears All Registry Entries for Its Frame

Each attached sound registration inserts its provider frame into the spatial-update registry without deduplicating existing entries. When one tracked sound is stopped, `FUN_0047b220` removes that sound's linked record and clears every registry slot that equals the provider frame. Any other active sound records still linked to that frame are then skipped by the periodic registry walk, so this path stops refreshing their positions. The other records remain linked to the frame and are reachable again if a later registration inserts the provider into the registry.

**Evidence.** Static disassembly of shipped `reference/LegoRR.exe`, SHA-256 `c3d8ce23f1aa21814950c77e713ec176599506d4e71758cf1cf709525e581e0f`. `FUN_0047b1a0` (`0x47b1a0`) always creates an object-linked sound record and stores its provider pointer in the first empty slot in `DAT_00533884..DAT_005338d0`; it does not check whether that provider already has an entry (finding 165). `FUN_0047b220` (`0x47b220`) removes the record for the stopped sound, then scans all 20 registry entries and zeroes each slot whose pointer equals that provider. `FUN_0047b390` (`0x47b390`) only calls `FUN_0047b410` for non-null registry entries, and that helper updates only records reachable from the registered frame's linked list (finding 162). The stop helper is reached through `FUN_0047ad30` when a tracked sound handle is stopped; finding 63 records this stop path.

This effect requires multiple active attached sounds to share a provider frame and one of them to stop. It is a static control-flow conclusion; no runtime case was induced.
