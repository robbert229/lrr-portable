# Finding 396 — CRT Process Startup, Termination, and Exceptions

This finding maps the 41 functions assigned to `platform-and-runtime/runtime-exceptions-and-process`. Evidence comes from the canonical decompile corpus (`docs/decompiles/full/LEGORR.full.c`). Caller/callee relationships are direct corpus calls unless identified as an inference. Several bodies are compiler-runtime fragments with incomplete names or recovered control flow; those limitations are called out rather than assigning undocumented semantics to every parameter or flag.

## Process startup and termination

- `_WinMainCRTStartup @ 0x0048f000` is supplied by VC5 `LIBC.LIB`'s `wincrt0.obj`; Reccmp reports 91.49% similarity. The startup flow installs an FS-linked exception frame, records version globals, checks runtime initialization, initializes descriptor and ANSI code-page tables, obtains the command line and environment, initializes argv/environment state, then calls VC5 `__cinit @ 0x0048e480` to run CRT initializer callbacks, including floating-point setup. It skips the executable-name portion of the command line, accounting for quoted names and DBCS lead bytes, reads startup information, and calls `WinMain @ 0x004777a0`. The target has custom exception-filter and registration handlers where the stock VC5 body uses `__XcptFilter` and `__except_handler3`; its startup structure otherwise follows the library routine. The WinMain result is passed to `_exit`.
- The entry path exits through `_exit(0xffffffff)` if command-line or environment acquisition fails. Otherwise it passes the `WinMain` result to `_exit`. `_exit @ 0x0048e4b0` and `__exit @ 0x0048e4d0` are VC5 `LIBC.LIB` entries from `crt0dat.obj`; their emitted wrappers exactly match the reference and pass `(code, 0, 0)` or `(code, 1, 0)` to `_doexit`, respectively.
- `_doexit @ 0x0048e4f0` is VC5 `LIBC.LIB` `crt0dat.obj`'s static termination routine; its 0xa4-byte instruction sequence matches the reference after relocations. It sets termination globals and runs callback ranges. If its second argument is zero, it first walks a dynamically registered callback list backwards, then invokes the range `[0x004a1018, 0x004a1020)`. It always invokes `[0x004a1024, 0x004a102c)`. If already in the termination state, it first calls `TerminateProcess` on the current process with the requested exit code. When the third argument is zero it marks termination and calls `ExitProcess`; otherwise it returns to its caller. Direct callers include `_exit` and `__exit`; the CRT startup path reaches it indirectly through `_exit`. The static symbol has no separate Reccmp PDB entry, but the linked body is present in the rebuilt executable.
- `CrtRunCallbackArray @ 0x0048e5a0` is an exact instruction match for VC5 `LIBC.LIB`'s private `_initterm` in `crt0dat.obj`. Although `_initterm` is static, the public `__cinit` entry calls it twice, so linking CRT startup pulls in the object and supplies the helper. MSVC builds omit the local implementation; portable builds keep the equivalent half-open callback walk.
- `ResetLevelAndExit @ 0x004250a0` and setup/loader paths call `CrtExit(0)`. In those callers the game intentionally enters the CRT exit flow; this does not establish whether the call represents a normal process shutdown or a recovery path in every context.

## SEH frames, scope tables, and unwind state

- `CrtExceptionFrameInstallAndDispatch @ 0x0048ed30` links a local frame into the FS exception chain, stores its filter/context fields, and invokes the dispatcher pointer at `DAT_0054919c` with the exception code and frame address. It restores or unlinks the frame on either recorded state path, then returns zero. `CrtSehExceptionDispatcher @ 0x00495410` is a direct caller.
- `___CxxFrameHandler @ 0x0048ec60` is supplied directly by VC5 `LIBC.LIB`'s `frame.obj`; Reccmp reports a 100% match. Its public runtime entry forwards to `___InternalCxxFrameHandler @ 0x00495090`. No direct caller is shown in the canonical corpus.
- `CrtExceptionFrameFilterInvoke @ 0x0048ed00` extracts fields from the installed frame and forwards them to `CxxExceptionHandlerDispatch @ 0x00495090`. `CallSettingFrame12 @ 0x0048eca0` builds an FS-linked frame whose filter is this helper, calls the recovered `__CallSettingFrame@12` routine, then restores the previous FS head.
- `CrtExceptionScopeFilterAndUnwind @ 0x0048ee00` checks exception flag bits `0x66`; when present, it sets a frame field at `+0x24` and returns filter result 1. Otherwise it dispatches through the C++ handler, calls `SehFrameUnwind` if that field remains zero, and invokes the filter pointer stored in the frame. The meanings of all tested bits and frame fields are not fully established in this slice.
- `SehScopeTableLookup @ 0x0048ee90` walks a scope table of 0x14-byte entries, selecting entries whose start/end range contains the instruction address. It returns the selected entry and writes the resulting scope bounds through two output pointers. Invalid scope progression calls `CrtUnexpectedHandlerInvokeAndTerminate`.
- `CrtSehExceptionDispatcher @ 0x00495410` first tries the registered C++ exception dispatcher when `DAT_0054919c` is nonzero. If that path does not report handling, it searches the SEH scope table for entries covering the instruction address; for eligible entries, it derives a handler record and calls `CrtSehUnwindAndInvokeHandler`.
- `CrtSehUnwindAndInvokeHandler @ 0x004955c0` optionally binds/copies a C++ catch object, calls `SehFrameUnwind`, unwinds local scopes to the selected target, advances the frame's current-scope index, and invokes the handler through `CrtSehHandlerCallWithFrame`. A nonzero handler result is passed to `CrtExceptionHandlerTransferAfterUnlink`.
- `CrtSehLocalUnwindToScope @ 0x004954e0` walks the frame's scope index toward a requested target. It updates the current-scope field before invoking each non-null cleanup callback through `__CallSettingFrame@12` with state `0x103`; invalid indices trigger the unexpected-handler path. `CrtLocalUnwindFromFrame @ 0x00496895` is a wrapper around `__local_unwind2` using frame fields at `+0x18` and `+0x1c`.
- VC5 `LIBC.LIB`'s `exsup.obj` supplies `__global_unwind2 @ 0x0048ef10`, `__local_unwind2 @ 0x0048ef52`, `__abnormal_termination @ 0x0048efba`, `__NLG_Notify1 @ 0x0048efdd`, and `__NLG_Notify @ 0x0048efe6`. The current Reccmp matches are 96.30%, 100.00%, 90.00%, 75.00%, and 85.71%, respectively. The first wraps `RtlUnwind`; the local-unwind helper advances the scope index before cleanup callbacks and records NLG state `0x101`. The target's `__NLG_Notify` body stores NLG values in the image's corresponding globals; the runtime versions use `__NLG_Destination`. `SehFrameUnwind @ 0x0048ec00` separately calls `RtlUnwind`, clears exception flag bit 1 in the exception record, and restores the FS chain head.
- `__abnormal_termination` returns 1 only when the active FS frame points at the expected local-unwind handler and its scope index still matches the frame state; otherwise it returns zero. The state recorded by the target's `__NLG_Notify @ 0x0048efe6` is sourced from registers and frame state; the exact external consumer is not identified here.
- VC5 `LIBC.LIB` `lowhelpr.obj` supplies the exact 0x4c-byte `__CallSettingFrame@12` body at `0x00495a90`, outside its two relocated calls to `__NLG_Notify1`. It records NLG state, invokes the function pointer, and reports state `2` after state `0x100`. The wrapper at `0x0048eca0` is a separate target function.

## C++ exception search, catch objects, and termination handlers

- `CxxExceptionHandlerDispatch @ 0x00495090` validates the exception metadata signature `0x19930520`. Depending on exception flags and frame state, it routes to `CxxExceptionHandlerSearch`, invokes a metadata-provided handler when present, or unwinds to the function's target scope. Invalid metadata goes to `CrtUnexpectedHandlerInvokeAndTerminate`.
- `CxxExceptionHandlerSearch @ 0x00495160` validates the current scope index, checks C++ exception records and metadata, and uses `SehScopeTableLookup` to examine handler entries covering the instruction address. It compares catch/type descriptors against the thrown-type list, applies matching attributes, and dispatches a match through `CrtSehUnwindAndInvokeHandler`. If no match is found, it may run destructor/terminate handling depending on its search/unwind mode; otherwise it delegates to `CrtSehExceptionDispatcher`.
- `CxxCatchObjectBindOrCopy @ 0x004957d0` checks source/destination memory ranges and catch metadata, then copies, adjusts, or binds the exception object according to descriptor flags and type information. It uses `CrtUnwindAddressResolve` for relative metadata references and `CrtExceptionHandlerTransferWithAtomicPrefix` for one recovered handler path. Exact C++ ABI meanings of all descriptor bits remain a follow-up item.
- `CrtUnwindAddressResolve @ 0x00495a60` starts from a base plus a relative metadata offset and, when the optional indirection index is nonnegative, resolves an additional pointer-relative displacement. It supports the metadata traversal used by catch-object processing.
- `CrtSehHandlerCallWithFrame @ 0x00495650` saves the active exception/context globals, invokes the filter/handler through `CallSettingFrame12`, then calls `CrtSehAbnormalTerminationCleanup` before restoring the FS chain.
- `CrtSehAbnormalTerminationCleanup @ 0x0049573a` restores saved frame data and exception globals. For the recognized C++ exception record and a particular frame/handler state, it calls `__abnormal_termination` and then `CrtSehDestructorInvoke`.
- `CrtSehDestructorInvoke @ 0x004959e0` reads a destructor callback from nested metadata and calls it through `CrtExceptionHandlerTransferWithAtomicPrefix` when both the record and callback are non-null.
- VC5 `LIBC.LIB` `trnsctrl.obj` supplies `?_JumpToContinuation@@YGXPAXPAUEHRegistrationNode@@@Z` at `0x0048ebb0` and `?_CallMemberFunction0@@YGXPAX0@Z` at `0x0048ebf0`. The first target body matches the archive's 0x36-byte continuation transfer outside relocated addresses; the second is an exact seven-byte match. Their decorated entries are selected through the C++ frame-handler dependency already pulled by `___CxxFrameHandler`.
- `CrtTerminateHandlerInvokeAndAbort @ 0x00495ae0` invokes the registered terminate handler at `DAT_005491a0` when non-null, then calls `_abort`. `CrtUnexpectedHandlerInvokeAndTerminate @ 0x00495b70` similarly invokes `PTR_FUN_004b22a4` when set, then continues through `CrtAbortAfterCallback` into the terminate-handler/abort path. `CrtAbortAfterCallback @ 0x00495bde` is a direct wrapper around that path.
- `_abort @ 0x004996f0` is VC5 `LIBC.LIB`'s `abort.obj` entry; the termination-handler path already calls the C `abort()` API, so MSVC builds link this implementation directly. It writes the runtime error message for code 10, calls the signal dispatcher with signal 22, and exits through `__exit(3)`. A second assigned `_abort @ 0x00495b4e` has a body that calls itself recursively; this looks like an unresolved thunk/decompile-boundary artifact rather than a useful implementation. Preserve this discrepancy until the address map or jump target is confirmed.

## Runtime diagnostics and fatal exits

- `__amsg_exit @ 0x0048f1a0` optionally enters the runtime-error callback sequence, displays the selected runtime error, and calls the `__exit` function pointer with code `0xff`.
- `CrtRuntimeErrorMessageEnterExit @ 0x004968b0` is VC5 `LIBC.LIB`'s `crt0msg.obj` `__FF_MSGBANNER`; its 0x40-byte body matches exactly apart from relocated references to `___error_mode`, `___app_type`, `__adbgmsg`, and `__NMSG_WRITE`. The MSVC build uses that runtime entry, while portable builds retain the local equivalent.
- `CrtRuntimeErrorMessage @ 0x004968f0` is VC5 `LIBC.LIB`'s `crt0msg.obj` `__NMSG_WRITE`; its message lookup, console output, and dialog paths match the target apart from relocated runtime data and API references. The MSVC build calls it directly; portable builds retain the local implementation. The MSVC source aliases `s_runtime_error_mode`, `s_runtime_error_console_mode`, and `s_runtime_error_callback` to the runtime's `___error_mode`, `___app_type`, and `__adbgmsg` globals so callers and runtime code share state.
- `___crtMessageBoxA @ 0x00499730` is supplied directly by VC5 `LIBC.LIB`'s `crtmbox.obj`; its linked body matches the target exactly outside relocated addresses. The MSVC build now calls this runtime entry, which lazily loads `user32.dll`, resolves `MessageBoxA`, `GetActiveWindow`, and `GetLastActivePopup`, caches those pointers, and displays the dialog. Portable builds retain the local implementation.
- `CrtSignalHandlerDispatch @ 0x0049aa10` is VC5 `LIBC.LIB`'s `_raise` from `winsig.obj`. The target body matches the runtime's signal-number dispatch table, handler lookup, default/ignore handling, FPE state reset, and callback invocation. The MSVC link explicitly pulls `_raise`; the existing `_abort` path calls it with signal 22.
- `CrtFatalMessageExit @ 0x00498340` calls VC5 `LIBC.LIB`'s `__amsg_exit(2)` in the MSVC build; portable builds use `abort` and retain a test observer hook. Its direct callers and the meaning of message code 2 are not resolved within this ticket.

## State and control-flow notes

- The process state is spread across FS-linked stack frames and globals. Frame setup links a local record; unwind helpers update scope state before callbacks; handler wrappers save and restore the exception globals around user/cleanup code.
- Normal process termination and abnormal termination share callback/message/abort helpers but differ in which callback ranges run and whether control returns. Exact CRT terminology for each `_doexit` parameter should be checked against broader cross-references before treating the values as named modes.
- Callbacks and exception handlers are indirect function pointers. Validation paths use `IsBadReadPtr`, `IsBadWritePtr`, and `IsBadCodePtr` wrappers in the C++ handler flow, but these checks do not prove that a callback is safe or valid after checking.
- The corpus provides no runtime tests for these original CRT internals; statements here describe recovered control flow and preserve uncertainty where decompilation is incomplete.

## Open questions and follow-up slices

1. Resolve both `_abort` entries, especially the self-recursive body at `0x00495b4e`, against raw disassembly and thunk/xref metadata.
2. Map every callback range and registration global used by `_doexit`; establish the precise semantics of its two mode parameters and reentrant termination path.
3. Trace the `DAT_0054919c` dispatcher installation and establish when C++ handling versus SEH scope-table handling is selected.
4. Decode C++ throw/catch metadata and scope-table field meanings, including the flags used by `CxxCatchObjectBindOrCopy` and `CxxExceptionHandlerSearch`.
5. Follow NLG state globals and the recovered jump-table targets for the two exception-transfer fragments.
6. Verify the error-message mode globals and the runtime message table, including the behavior and callers of message code 2.
7. Confirm whether `__global_unwind2` and `CrtFatalMessageExit` have callers outside the canonical manifest or represent compatibility/support exports.
