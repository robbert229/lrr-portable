# Finding 461 — Weapon Definitions and Indexed Lookups

The seven assigned routines load weapon definitions into per-type records, resolve names to type indices, and read configured weapon values either directly or through entity-specific indexed tables. The direct behavior is in the checked-in decompile [`LEGORR.full.c`](../decompiles/full/LEGORR.full.c). Findings 225, 231, 247, 250, 256, and 331 already record portions of the loader/accessor use; this map connects the storage defaults to the lookup paths and startup/gameplay callers.

## Weapon definition loading

`WeaponTypeConfigLoad @ 0x0046eb80` stores the supplied config handle, counts entries under `WeaponTypes`, then allocates a `0x4b68`-byte record per type and a parallel name-pointer array. It initializes per-record configuration grids to `-1.0`, a number of scalar fields to zero, one field to `10.0`, and the per-wall-type default array to `5.0`. It then iterates each weapon definition and its nested entries. Keys visible in the body include `SlowDeath`, `RechargeTime`, `DefaultDamage`, `DischargeRate`, `WeaponRange`, the unknown scalar at `+0x14`, `WallDestroyTime_*` entries, and other nested type/level keys. The loader stores the type name in the parallel name array and stores parsed numeric entries in type/level/index grids. The meaning of every grid dimension and the unnamed scalar are not established by the body alone.

The four scalar getters expose fields in the per-type record footer: `WeaponTypeGetRechargeTime @ 0x0046f110` reads `+0x4b0c` (footer offset `+0x0c`), `WeaponTypeGetDischargeRate @ 0x0046f140` reads `+0x4b14` (footer `+0x14`), `WeaponTypeGetRange @ 0x0046f170` reads `+0x4b1c` (footer `+0x1c`), and `WeaponTypeGetWallDestroyTime @ 0x0046f1a0` reads the per-type wall array at `+0x4b20 + wallIndex*4`. Finding 331 links the first three fields to the `RechargeTime`, `DischargeRate`, and `WeaponRange` config keys; the loader body also shows the relevant assignments. The API name “wall destroy time” follows its use of the `WallDestroyTime_*` key family; the wall-index enum remains unverified.

`GameConfigInit @ 0x0041fb50` calls the loader with its config state and the shared config handle. In gameplay, the projectile/slot setup path in `KindEffectSlotInitDispatch @ 0x004420d0` resolves `Lazer`, `Pusher`, and `Freezer` through `ObjectTypeNameIndexFind`, and uses `WeaponTypeGetRechargeTime` for a resulting entity field (Finding 256). Other paths use `WeaponTypeGetRange` to bound ray/collision work (Findings 249 and 256).

## Name and entity-indexed lookups

`ObjectTypeNameIndexFind @ 0x0046f0d0` performs case-insensitive comparison against the loaded name-pointer array. With no loaded weapon types it returns `1`; on a match it returns the zero-based index; on a miss it returns `count + 1`. This is a sentinel-bearing lookup, so callers must distinguish a valid index from the miss result. Findings 231, 247, 250, and 256 cite callers that pass configured object/weapon names into it.

`EntityIndexedFloatLookupWithMinusOneFallback @ 0x0046f1d0` uses the entity's type, level, and selected record index to address a weapon-type-specific float grid. If that selected grid value is exactly `-1.0`, it returns the per-type `DefaultDamage` fallback at `+0x4b10`; otherwise it returns the entity-indexed value. The indexed cell is calculated from the type's `0x12da`-dword region, the entity kind's `0x3c0`-byte section, the level's `0x40`-byte (`0x10`-dword) section, and the selected index. `TypeMotionScaleApplyDispatch @ 0x0046f270` consumes this helper and uses the returned value in its impulse path (Finding 258); `CellTypeSpeedMultiplierResolve @ 0x00433180` also reads a configured per-entity value on its rock-fall branch (Finding 250). The record dimensions and sentinel are direct evidence; the semantic identity of every indexed stat is not.

## Limits and follow-up

The loader and readers establish allocation stride, defaults, known key-to-field assignments, name lookup behavior, sentinel fallback, and representative callers. They do not establish a complete weapon schema, all key units, the named wall-index set, or whether `-1.0` is used for every optional per-entity stat. Existing findings already cover concrete launch/ray consumers, so no duplicate implementation ticket is justified. A useful follow-up would compare the loader's complete key set against shipped weapon configuration examples and verify the wall-index mapping; that source-data evidence is outside these function bodies.
