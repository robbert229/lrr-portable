# Finding 430 — Scene Object, Action, and Animation Lifecycle

Issue #187 assigns 81 procedures in the scene-object-animation area. Most core behavior was already traced across findings 11, 25–43, 49, 244–256, and 349–401. This finding joins those call paths, fills the small gaps in helper behavior, and records the remaining boundary questions. Evidence is static analysis of the shipped `reference/LegoRR.exe`; names remain descriptive labels for observed code, and interface-slot semantics are left unresolved where the caller/callee evidence does not identify them.

## The object lifecycle and neighboring owners

A DDiScene object is a pooled record with a kind-specific payload and paired interfaces. `DDiSceneObjectDestroy` (`0x00472a40`, wrapper; `0x00472a50`, implementation) first takes the unlink path for non-kind-6 objects, then performs kind-dependent payload cleanup and interface releases before returning the record to the DDiScene free list. The kind-3/4 auxiliary-payload branch with mode zero clears its payload's `+0x10` field and returns early. Entity teardown calls the wrapper before recycling the entity; pool shutdown walks live records with the destroy implementation in shutdown mode. Findings [25](25-ddscene-object-runtime.md), [29](29-ddscene-entity-teardown.md), [30](30-ddscene-clone-reuse.md), [31](31-ddscene-reuse-callback-order.md), and [84](84-entity-teardown-dispatches-type-specific-payload-cleanup.md) document allocation, reuse, and teardown ordering. Static evidence does not prove that every detached object is unreachable to every later draw or callback path.

Visual loading feeds that lifecycle. `EntityVisualLoadACT` (`0x00472cd0`) and `EntityVisualKindDispatch` (`0x00475930`) select a loader by visual-kind name and construct the corresponding scene object. `EntityVisualResourceLoad` (`0x00473690`) resolves a named child resource and returns the loaded interface; the resource is retained/locked by the caller where needed. `DDiSceneObjectKindModeSetup` (`0x00473560`) allocates a kind-1 object and initializes it through the render interface, with setup parameters 2–4 selecting distinct initialization values and a separate mode-1 setup path. `DDiSceneLightCreate` (`0x004734f0`) allocates kind 5, calls the scene-light interface slot `+0x30` with the supplied light arguments, and records the scene-light interface in the object payload after successful creation. These names describe the observed dispatch and slot use; the full semantic contract of the renderer methods is not established.

Owner association is a separate link: `SceneObjectOwnerSet` (`0x00473da0`) and `SceneObjectOwnerGet` (`0x00473db0`) write/read the object `+0x20` owner field, and `SceneObjectOwnerLinkEnsure` (`0x00475880`) creates or preserves the owner relationship used by entity visual setup. The scene-end callback registered during boot follows this link to set an entity completion bit (finding 26); the entity-side consumers are documented in finding 27. `SceneObjectOwnerLinkRelease` (`0x00489750`) performs the paired interface releases involved in owner-link cleanup. `DDiSceneObjectAttachOrUnlink` (`0x00475710`) updates the paired scene interfaces for attach and null-argument unlink calls; `DDiSceneContextGet` (`0x004757a0`) returns the current scene context, and `DDiSceneObjectArgumentsNormalize` (`0x00475900`) supplies the default context when an object argument is null (finding 25). `SceneObjectFirstNonKind6ChildGet` (`0x00475830`) scans for the first child outside the kind-6 case. Findings [28](28-ddscene-entity-ownership.md), [26](26-ddscene-animation-hooks.md), and [27](27-scene-done-flag-consumers.md) show the relationship and callback consumer path. They do not establish a runtime race between teardown and a later frame callback.

## Actions, frame records, and callbacks

`SceneActionNamePresent` (`0x00473340`) and `SceneActionNameSet` (`0x00473370`) query and update the paired action-name channels. The update path propagates a selected name into both channel records; the channel state then participates in activity transitions and action-entry sample selection (findings 35, 36, and 42). `DDiSceneObjectArrayGrow` (`0x004759f0`) expands the pooled scene-object array when allocation needs more slots (finding 25). `SceneActionRecordActFrameScan` (`0x00475a70`) walks the two action-entry containers for a kind-4 object, reads entry names through their interfaces, and matches the literal `ActFrame`; it can count matches or fill the caller's output buffer. `DDiSceneActFrameRecordParse` (`0x00475d10`) formats the corresponding key, reads it from the supplied configuration/resource interface, parses or resolves the value, and creates the frame-record hook on success. Finding 12 describes the `.ae`/block-text representation, and finding 244 traces the `ActFrame` scan callers.

`DDiSceneFrameRecordFind` (`0x00475e40`) looks up the frame/action record for an object and action entry; the draw worker uses it to select the current record (finding 26). `DDiSceneAnimationCallbacksSet` (`0x00475c00`) lazily creates a 16-byte callback/payload record, then replaces only nonzero callback/interface arguments in an existing record. `DDiSceneAnimationHookCreate` (`0x00475f70`) creates an animation hook from the parsed frame information; `SceneObjectSetFormattedString` (`0x00476270`) formats a string and routes it through that hook-creation path. `CallbackRecordSetFlag10AndRefresh` (`0x00475e10`) sets bit `0x10` on a callback record and refreshes its associated interface state. `DDiSceneTimedHookDispatch` (`0x004897e0`) performs the timed callback dispatch used by the frame path. The callback gates and timing conditions are detailed in findings [26](26-ddscene-animation-hooks.md), [34](34-ddscene-failed-init-retains-end-hook.md), [41](41-advisor-animation-window.md), [42](42-ddscene-sample-hook-consumption.md), and [43](43-ddscene-end-hook-repeatability.md); those analyses distinguish static eligibility from runtime callback frequency.

`DDiSceneAdvanceByTime` (`0x00475120`) advances an object's time and reports whether the object has reached its end condition. `DDiSceneFrameUpdateAndCallbacks` (`0x00475140`) selects a kind-specific frame/action record, advances or evaluates its timing, dispatches registered sample/end hooks when their gates match, and performs the draw-side update. `DDiSceneApplyActFrameTiming` (`0x00475300`) applies the timed-hook path only when object flag `0x20` is set; for kinds 3 and 4 it obtains the associated action/frame record, reads its `+0x1c` value and `+0x18` duration, and passes those to `DDiSceneTimedHookDispatch`. `DDiSceneObjectLengthGet`, `DDiSceneObjectFramePositionGet`, `DDiSceneActionRecordField1CGet`, `DDiSceneActionRecordField0CGet`, `DDiSceneAnimationDurationGet`, `DDiSceneAnimationStateGet`, and `DDiSceneAnimationLastFrameGet` (`0x00475390`, `0x004753f0`, `0x00476160`, `0x00476180`, `0x004761a0`, `0x004761e0`, `0x00476200`) expose the timing and frame-record fields consumed by that path (findings 25, 26, and 41).

`DDiScenePayloadRelease` (`0x00475c80`) frees or releases the payload according to object kind: kind 4 frees its frame/action payload, kind 5 releases the light interface, kind 1 releases an attached interface through the owning render interface, and kind 8 dispatches its paired-resource cleanup. It then frees and clears the payload pointer. `AttachedObjectDataReleaseAndClear` (`0x004760e0`) enumerates attached child records, releases the child-owned allocation where present, and frees the temporary enumeration record. These kind-specific release paths complement the destroy order described in finding 29.

## Transforms, bounds, resources, and draw boundaries

The assigned transform helpers are a bridge from scene-object methods to lower rendering interfaces. `RenderObjectHierarchyFloat3Set` (`0x00474e90`), `SceneObjectCoordinateTransformInPlace` (`0x00475070`) and `SceneObjectCoordinateTransformToOutput` (`0x00475090`), `RenderObjectSetPackedRgbaFromFloatChannels` (`0x004750b0`), `DDiSceneObjectPositionSet` (`0x00475430`), `DDiSceneObjectPoseMethodDispatch` (`0x00475470`), `DDiSceneMoveOrPose` (`0x004754c0`), `RenderObjectRotateAxis` (`0x00475580`), `SceneFrameScaleSet` (`0x004755b0`), `CameraTeleportOrOffset` (`0x004755e0`), `RenderObjectSetIdentityTransform` (`0x00475610`), `SceneObjectTransformMatrixSet` (`0x004756b0`), `SceneObjectBoundsUnion` (`0x00474f10`), and the associated matrix/point helpers update positions, rotations, scale, packed color, or transform outputs. `SceneObjectBoundsUnion` (`0x00474f10`) initializes a six-value box through one interface call, enumerates child render objects, obtains each child's box, and expands the minimum and maximum coordinates. Findings 241, 242, 245, 247, 250, 252, and 255 trace the caller-side pose and transform flows; finding 255 specifically shows the point conversions and matrix installation used by the scene-pose path.

`DDiSceneResourceNameResolve` (`0x00476770`), `DDiSceneResourceExists` (`0x004767e0`), and `DDiSceneResourceOpen` (`0x00476850`) resolve a name through the scene resource interface and expose separate resolve, availability, and open operations. `TypedChildResourceScalarGet` (`0x004757f0`) reads a scalar from a typed child resource; `SceneObjectFirstNonKind6ChildGet` (`0x00475830`) returns the first child that is not kind 6. `SceneObjectQueryValueIfReady` (`0x00476f70`) returns a value only after its readiness predicate succeeds. `DDiSceneDrawBegin` (`0x00477010`) and `DDiSceneDrawEnd` (`0x00477150`) bracket the scene's render-interface work; `DDiSceneCurrentObjectSet` (`0x00477240`) updates the current-object state used by the draw path, and `DDiSceneRenderSurfacePoolGrow` (`0x00477370`) expands the surface-record pool. Findings 25, 49, and 251 cover the draw boundary and related render dispatch.

The names `SceneObjectRegistryTeardown` (`0x0047d430`) and `SceneObjectRegistryReleaseAll` (`0x0047e130`) label a global table/pool cleanup path. The teardown helper first calls the release-all sweep, frees each non-null table allocation, and resets the table count and adjacent global state. The sweep walks the configured table entries in `0x20`-byte steps and sends entries whose `+0x1c` self-pointer is valid to `ImageSurfaceRelease` (`0x0047d470`), which releases the interface and links the record onto the image-surface free list. The observed target is therefore a renderer/image-surface record pool, not the scene-object owner link. The low-level renderer findings provide more context on the recycled surface records (finding 274 and the UI render fifth-pass evidence).

## Additional small helpers in the assigned set

- `LightInterfaceCallSlot40` (`0x00473460`), `LightInterfaceCallSlot3C` (`0x00473480`), and `LightInterfaceCallSlot38` (`0x004734a0`) call the corresponding vtable slots on the light interface at object `+0x0c` and return whether the call returned zero. The slot meanings remain unknown.
- `AdvisorCompanionTransformApply` (`0x004734c0`) applies the companion transform through the scene object's transform interface; its caller and input relation are described in finding 40.
- `SceneObjectWrappedPointerGet` (`0x00473680`) returns the first pointer-sized field of its wrapper; `EntityFlag80Set` (`0x00473b20`) sets or clears bit `0x80` at object `+0x14`; `SceneObjectFlagBit3Get` (`0x00473ba0`) tests bit 3 of the object flag word.
- `VideoObjectAspectRatioGet` (`0x004756d0`) and `RenderInterfaceTransformPoint` (`0x004772b0`) are scalar/point query helpers exposed by neighboring video/render interfaces.
- `RenderInterfacePairUpdate` (`0x00476220`), `ScenePropertyPrimaryValueGet` (`0x00476120`), `ScenePropertySecondaryValueGet` (`0x00476140`), `ScenePropertyFloatAt14Get` (`0x004761c0`), and `ScenePropertyValueAt08Get` (`0x00476310`), plus `ScenePropertyOwnedBufferRelease` (`0x004762f0`) relay or release interface-backed property values; findings 349 and 352 trace their field and ownership behavior.
- `SceneNodeTransformMatrixApply` (`0x004882e0`) applies a supplied matrix through the scene-node interface. `SceneHierarchyInterfaceRegisterRecursive` (`0x004887c0`) registers the interface across a node and recursively visited children (finding 246).
- `FUN_00475500` and `FUN_004897d0` remain conservatively named. Their callers and observed argument flow are covered in findings 241, 246, 249, 250, and 256; the available evidence does not establish a more meaningful semantic name.

## Assigned-function inventory and follow-up

All 81 assigned addresses are covered by the function descriptions above and the linked findings. The generated function-area and coverage-ledger rows for these addresses predate this finding; the README findings index/range is the only index updated here.

The remaining questions are the semantic contracts of the light-interface slots, the exact ownership rules for kind-specific auxiliary payloads across every construction path, and the runtime ordering between object detach, draw, and timed callback dispatch. Existing static evidence narrows those questions but does not justify an implementation slice by itself, so this investigation creates no implementation follow-up issue.
