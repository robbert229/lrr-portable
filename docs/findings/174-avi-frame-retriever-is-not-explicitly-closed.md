# Finding 174 — AVI Frame Retriever Has No Explicit Close Path

The AVI constructor stores the handle returned by `AVIStreamGetFrameOpen` in the movie object. The destructor `FUN_0047e9a0` releases the `AVIStream` handle and destroys the surface-side object, but does not pass the saved frame-retriever handle to a close routine. The executable's AVIFIL32 imports include `AVIStreamGetFrameOpen` and `AVIStreamGetFrame`, but no `AVIStreamGetFrameClose` import, and no other visible cleanup call targets the saved retriever field.

Microsoft documents `AVIStreamGetFrameClose` as releasing resources used to decompress video frames and as taking the handle returned by `AVIStreamGetFrameOpen`. The shipped movie code therefore has no explicit cleanup for those decoder resources. Whether the particular AVIFIL32 implementation also reclaims them indirectly when `AVIStreamRelease` is called is not established by the binary or this API contract, so this finding does not claim a measured runtime leak.

**Evidence.** Shipped `reference/LegoRR.exe`, SHA-256 `c3d8ce23f1aa21814950c77e713ec176599506d4e71758cf1cf709525e581e0f`. Constructor storage and destructor behavior are in `FUN_0047e800`/`FUN_0047e9a0` at `0x47e800`/`0x47e9a0` in `docs/decompiles/full/LEGORR.full.c`. `objdump -p reference/LegoRR.exe` lists imports `AVIStreamGetFrameOpen`, `AVIStreamGetFrame`, and `AVIStreamRelease`, with no `AVIStreamGetFrameClose`. Microsoft's [`AVIStreamGetFrameClose` documentation](https://learn.microsoft.com/en-us/windows/win32/api/vfw/nf-vfw-avistreamgetframeclose) says it releases the frame-decompression resources and invalidates the open handle. Finding 69 records the staged constructor and destructor paths.
