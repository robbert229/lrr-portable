# Finding 395 — CRT and OS File/Stream I/O

This finding maps the 39 functions assigned to `platform-and-runtime/runtime-file-streams`. Evidence is the canonical decompile corpus (`docs/decompiles/full/LEGORR.full.c`); caller/callee claims below refer to direct calls in that corpus unless marked as an inference. The CRT stream/file records are interpreted from their repeated field access patterns, and flag meanings are kept literal where not established.

## Descriptor table and Win32 handles

- `CrtFileDescriptorTableInit @ 0x004965d0` allocates a first table of 32 eight-byte descriptor slots, initializes handles to `-1`, flags to zero, and a per-slot byte to line feed. It reads inherited descriptors from `STARTUPINFO.lpReserved2`, caps the inherited count at `0x800`, and allocates additional 32-slot blocks as needed. It then installs stdin/stdout/stderr from `GetStdHandle` when not inherited and calls `SetHandleCount`. The CRT `entry @ 0x0048f000` calls it.
- `CrtFileDescriptorAllocate @ 0x00498fe0` scans the 32-slot blocks for a slot whose open bit is clear, marks its handle `-1`, and returns the global descriptor index. If it reaches a missing table block, it allocates and initializes another 32-slot block and extends `DAT_0076dec0` by 32. Exhaustion or allocation failure returns `-1`. The VC5 x86 build now links `osfinfo.obj`'s externally visible `__alloc_osfhnd` (91.78% Reccmp); portable builds retain the local table implementation.
- `CrtFileDescriptorSetHandle @ 0x004990a0` stores a Win32 handle only into a valid descriptor slot whose handle is `-1`. When `DAT_004afd64 == 1`, descriptors 0–2 also update the matching process standard handle; stdout/stderr additionally update their initial table slots. The VC5 x86 build now links `osfinfo.obj`'s `__set_osfhnd` (92.11% Reccmp); portable builds retain the local table implementation.
- `CrtFileDescriptorHandleGet @ 0x004991f0` is VC5's `_get_osfhandle` in the MSVC image; the compatibility name now resolves directly to that runtime entry (86.67% Reccmp). Portable builds retain the descriptor-table validation and error update.
- `CrtFileDescriptorCloseSlot @ 0x00499150` clears an open descriptor slot to `-1`, and optionally clears the process standard handle for descriptors 0–2. It does not itself call `CloseHandle`. The VC5 x86 build now links `osfinfo.obj`'s `__free_osfhnd` (90.62% Reccmp); portable builds retain the local table implementation.
- `CrtFileDescriptorClose @ 0x00494d10` now resolves directly to VC5 `LIBC.LIB`'s `_close` from `close.obj` in the MSVC image (94.44% Reccmp); `/include:__close` keeps it linked. Its body validates descriptor bounds/open state, handles aliased stdin/stdout descriptors sharing the same OS handle, closes a non-`-1` handle, clears the slot and its flags, and maps any Win32 error. Portable builds retain the local equivalent. Failed opens in `Win32FileDescriptorOpen` use it for cleanup. `FileResourceHandleClose @ 0x0048eae0` is VC5 `LIBC.LIB`'s `_fclose` from `fclose.obj`; its body flushes/releases the stream buffer, closes the descriptor through `_close`, and releases an owned stream buffer.
- `CrtFileDescriptorFlag40Get @ 0x00498b40` now resolves directly to VC5 `LIBC.LIB`'s internal `__isatty` entry from `isatty.obj` (90.48% Reccmp), including its `0x40` mask return. Portable builds retain the descriptor-table lookup. The stream close/write paths and standard-stream setup consult it.
- `CrtFileDescriptorFlag80SetOrClear @ 0x0049aea0` now resolves directly to `_setmode` (90% Reccmp); portable builds retain the local flag update. `Win32FileDescriptorResize @ 0x0049a890` saves and restores this mode around its zero-fill extension writes.
- `Win32FileDescriptorOpen @ 0x00499240` now maps directly to VC5 `LIBC.LIB`'s `_sopen` entry, with `/include:__sopen` retaining it. The portable fallback translates CRT access/share/create/attribute flags into `CreateFileA` arguments, allocates a descriptor, creates the OS handle, rejects invalid file types, records descriptor flags, and returns the descriptor number. It also performs append/text-mode setup through seek/read/resize helpers. `StdFileOpen @ 0x00494e30` calls it. The latest Reccmp report does not emit this address as a matched function symbol.
- `Win32FileDescriptorSeek @ 0x00496c00` now resolves directly to VC5 `LIBC.LIB`'s `_lseek` from `lseek.obj` (91.43% Reccmp); `/include:__lseek` retains it. Portable builds keep the local Win32/POSIX equivalent.
- `Win32FileDescriptorResize @ 0x0049a890` is VC5 `LIBC.LIB`'s `_chsize` from `chsize.obj`. Its body preserves the current position, measures end-of-file, truncates with `SetEndOfFile` when the target is smaller, or writes zero-filled chunks of up to `0x1000` bytes to extend it, then restores the prior position and mode flag. The MSVC link explicitly pulls `_chsize`; `Win32FileDescriptorOpen` uses it when establishing append behavior.
- `Win32ErrorMapToErrno @ 0x00496ee0` is VC5 `LIBC.LIB`'s `__dosmaperr` on MSVC x86; the shim now aliases directly to `_dosmaperr` and retains it with `/include:__dosmaperr`. Portable builds keep the local error-table and fallback-range mapping. Descriptor close/seek/read/write and several filesystem callers use it.
- `GameFileDelete @ 0x0048f650`, `FileSetReadOnlyAttribute @ 0x0048f680`, and `GameDirectoryCreate @ 0x0048f6d0` are VC5 `LIBC.LIB`'s `_remove` (`unlink.obj`), `_chmod` (`chmod.obj`), and `_mkdir` (`mkdir.obj`) implementations. Their instructions match the target wrappers, including Win32 error conversion through `__dosmaperr`; the MSVC link explicitly pulls these archive members.
- `CurrentDirectoryGet @ 0x0048fa00`, `DriveCurrentDirectoryGet @ 0x0048fa20`, and `DriveLetterRootTypeAvailable @ 0x0048fb50` are VC5 `LIBC.LIB`'s `_getcwd`, `_getdcwd`, and private `__validdrive` from `getcwd.obj`. Their target instructions match the archive bodies, including path validation, buffer sizing, and `GetDriveTypeA` checks; `_getcwd` pulls the shared object into the MSVC link.
- `PathResolveFull @ 0x0048ffa0` is VC5 `LIBC.LIB`'s `_fullpath` from `fullpath.obj`. The body matches the target, including use of `_getcwd` for an empty input and CRT allocation/error behavior; the MSVC link explicitly pulls the archive member.
- `AssetPathComponentsParse @ 0x00490090` is VC5 `LIBC.LIB`'s `_splitpath` from `splitpat.obj`. The archive body matches the target's drive, directory, basename, and extension scan, including the same bounded component copies and multibyte lead-byte check; the MSVC link explicitly pulls the archive member.
- `CrtFindHandleClose @ 0x0048f950` now resolves directly to VC5 `LIBC.LIB`'s `findfile.obj` function `__findclose` (90% Reccmp). Its body calls `FindClose`, sets `errno` to `0x16` on failure, and returns `-1` or zero. `/include:__findclose` retains the entry.
- `GameFileMetadataFind @ 0x0048f700`, `FileFindNextRecord @ 0x0048f830`, and `FileTimeToLocalDateTimeStamp @ 0x0048f970` are also provided by that same VC5 `findfile.obj`: `_findfirst`, `_findnext`, and `__timet_from_ft`. Their archive bodies match the target's Win32 enumeration, metadata layout, error mapping, and FILETIME conversion. The `_findclose` reference pulls the object into the MSVC link, so these entries need no local stubs.

The descriptor records are organized in blocks of 32, with a handle dword and flag/state bytes at offsets `+4` and `+5`. This layout is direct from table initialization and descriptor access; interpreting every flag bit as a particular CRT mode requires additional cross-references.

## OS-level read, write, seek, and stream buffering

- `StdFileOpenIntoHandle @ 0x0048eb60`, `FileOpenAndReadWholeStream @ 0x0048eb90`, `StdFileOpen @ 0x00494e30`, and `StdFileHandleAcquire @ 0x00495000` are VC5 `LIBC.LIB`'s `__fsopen`, `_fopen`, `__openfile`, and `__getstream`. Their bodies match the target's mode parsing, descriptor open, `FILE` initialization, and stream-slot allocation. Forcing `_fopen` pulls the required `fopen.obj`, `_open.obj`, and `stream.obj` entries into the MSVC link.
- `StreamedAudioFileLengthGet @ 0x0048f2b0` and `FileResourceHandleSeek @ 0x0048f460` are VC5 `LIBC.LIB`'s `_ftell` (`ftell.obj`) and `_fseek` (`fseek.obj`). Both instruction bodies match the archive, including stream buffer/text-mode position adjustment, flushing, origin validation, and descriptor seek. The MSVC link explicitly pulls both entries; `_fseek` also pulls its `_ftell`, `__flush`, and `__lseek` dependencies.
- `GameFileWrite @ 0x0048f500` and `GameFileReadBuffered @ 0x0048fb90` are VC5 `LIBC.LIB`'s `_fwrite` (`fwrite.obj`) and `_fread` (`fread.obj`). Their target bodies follow the runtime's element-count logic, buffered copies, direct descriptor I/O, and per-character fallback. The MSVC link explicitly pulls both stream-I/O entries.
- `BufferedStreamReadLine @ 0x0048fe50` is VC5 `LIBC.LIB`'s `_fgets` from `fgets.obj`. Its body matches the runtime's size validation, buffered character reads through `__filbuf`, newline stop, EOF handling, and NUL termination. The MSVC link explicitly pulls `_fgets`.
- `BufferedStreamGetByte @ 0x0048fe20` is VC5 `LIBC.LIB`'s `_fgetc` from `fgetc.obj`. It decrements the stream count and advances the buffer pointer when data is ready, then calls `__filbuf` when the buffer is empty. The MSVC link explicitly pulls `_fgetc`.
- `Win32FileDescriptorRead @ 0x00497130` now resolves directly to VC5 `LIBC.LIB`'s `_read` from `read.obj` (97.02% Reccmp); `/include:__read` retains it. Portable builds keep the local Win32/POSIX equivalent. `CrtStreamReadByte`, `GameFileReadBuffered`, and `Win32FileDescriptorOpen` call it.
- `Win32FileDescriptorWrite @ 0x00496cc0` now resolves directly to VC5 `LIBC.LIB`'s `_write` from `write.obj` (95.56% Reccmp); `/include:__write` retains it. Portable builds keep the local Win32/POSIX equivalent. Stream flush, stream write, game-file write, and resize paths call it.
- `CrtStreamReadByte @ 0x00497040` maps directly to VC5 `LIBC.LIB`'s `__filbuf` on MSVC x86 (97.85% Reccmp); the portable fallback checks stream readability/EOF flags, refills through the descriptor read helper, returns the first byte while retaining the rest in the stream buffer, and updates EOF/error flags. `GameFileReadBuffered` and the byte/line wrappers call it.
- `BufferedStreamGetByte @ 0x0048fe20` consumes a byte from the stream buffer when available and otherwise refills through `CrtStreamReadByte`. The formatted-input helpers at `0x00494c70` (`__inc`), `0x00494ca0` (`__un_inc`), and `0x00494cc0` (`__whiteout`) are static functions in VC5 `LIBC.LIB`'s `input.obj`, linked with `__input`; their reference implementations are supplied by that archive object on MSVC builds.
- `BufferedStreamReadLine @ 0x0048fe50` reads at most `size-1` bytes, stops after LF, NUL-terminates, and returns null only for an invalid nonpositive size or EOF before reading any byte. `GameFileReadLineDispatch @ 0x0047fd40` calls it.
- `CrtFlushStreamBuffer @ 0x0048fd20` maps directly to VC5 `LIBC.LIB`'s `__flush` on MSVC x86 (100% Reccmp); the portable fallback writes pending output bytes, resets the buffer pointers/count, and sets the stream error bit on a short write. `FileResourceHandleClose`, `FileResourceHandleSeek`, `GameFileWrite`, and the buffer-release helper call it.

## Formatted input and pushback

- `VsscanfParseInput @ 0x00490070` constructs a local byte-stream record around a caller-provided string and calls `CrtFormattedScanV @ 0x00493ef0`; `FileTokenListLoadAndTreeScan @ 0x004802d0` calls it.
- `MarkupIntegerTokenParse @ 0x0048e890` is VC5 `LIBC.LIB`'s `_sscanf` from `sscanf.obj`. Its wrapper computes the input string length, builds the same stream state as the archive, and calls the shared `__input` scanner. The MSVC link explicitly pulls `_sscanf`.
- `CrtFormattedScanV @ 0x00493ef0` parses a scanf-style format against the stream abstraction. It skips classified whitespace, handles literal matching and format width/suppression/length flags, and has paths for character/string/scanset, signed/unsigned/octal/hex/pointer, floating-point, and `%n` conversions. It uses `ScanStreamGetChar`, `StreamPushbackChar`, `StreamSkipClassifiedChars`, character-classification helpers, and multibyte conversion; it tracks consumed characters and successful assignments and returns the assignment count (or `-1` for input failure before a conversion). `VsscanfParseInput` and the `_sscanf` wrapper call it.
- `CrtScanFormatCharNormalize @ 0x00494c30` is VC5 `LIBC.LIB`'s private `__hextodec` helper in `input.obj`. It leaves decimal digits intact and maps non-digit format/input characters by case-normalizing and subtracting the alphabetic offset, which makes letters usable as hexadecimal digit values.
- `StreamPushbackChar @ 0x00494ca0` ignores EOF (`-1`) and otherwise delegates to `CrtStreamUngetByte @ 0x00498f50`.
- `StreamSkipClassifiedChars @ 0x00494cc0` reads one character and continues while `FUN_00498f00` classifies it as whitespace, incrementing the consumed-character count; the first nonspace is returned to the caller.
- `CrtStreamUngetByte @ 0x00498f50` aliases directly to VC5 `LIBC.LIB`'s `_ungetc` on MSVC x86 (100% Reccmp). Portable builds retain the local stream-state implementation, which accepts a byte only for readable streams, moves the read pointer backward, increments the available-byte count, and enforces the descriptor-flag `0x40` matching-byte case.
- `FormatArgumentReadDword @ 0x00491430`, `FormatArgumentReadWord @ 0x00491470`, and `FormatArgumentReadInt64 @ 0x00491450` read varargs slots and advance the cursor by 4, 4, and 8 bytes. The 64-bit helper returns raw integer bits in `EDX:EAX`; it is not an x87 `double` return. The word helper consumes one four-byte varargs slot, despite only reading its low word. Their instruction bodies match VC5 `output.obj`'s static `_get_int_arg`, `_get_short_arg`, and `_get_int64_arg` helpers; the MSVC build gets them with `__output`, while portable builds retain local copies.
- The corpus alias `CrtScanfNumericConversionAssign @ 0x00498ce0` is a floating-point exception dispatcher, not a stream scanner: its 0x120-byte body exactly matches VC5 `LIBC.LIB`'s `__87except` in `87except.obj`, and the math-error frame helpers at 0x491f80 and 0x491f97 call it. The MSVC build links this runtime function directly.

## Error and state flow

- Descriptor operations validate the open bit before touching a handle. Invalid descriptors set CRT error `9`; `Win32ErrorMapToErrno` preserves the raw Windows error separately and maps it to the CRT error global.
- Read/write/seek return conventions differ by layer: descriptor read returns `-1` on error and zero at EOF; buffered stream reads also return `0xffffffff` for EOF/error with flags carrying the distinction; short writes set the stream error flag.
- Text-mode newline translation is performed by descriptor read/write helpers, while stream functions manage buffers and stream flags. This separation is direct from the call graph and is important when tracing byte counts or seeking.
- Descriptor state lives in global table blocks; `DAT_0076dec0` is the descriptor upper bound/count. Stream state is separate and includes buffer pointers, counts, descriptor number, and flags. The precise meaning of all stream flag bits is not fully recoverable from these functions alone.

## Open questions and follow-up slices

1. Reconcile the assigned name `CrtFileStreamClose @ 0x004908a0` with its observed write behavior and wider callers.
2. Trace every descriptor and stream flag bit across initialization, open, read, write, seek, close, and standard-stream installation; confirm which bits correspond to text mode, EOF, ownership, buffering, and append.
3. Establish the exact `STARTUPINFO.lpReserved2` descriptor inheritance layout and maximum-count handling, including whether the `0x800` cap is an entry count or byte-related cap.
4. Trace how the math-error handler and `__87except` paths populate and consume the exception record fields.
5. Check partial writes and text-mode CRLF conversion when the OS writes only part of a translated chunk; the helper returns translated counts but no test evidence is part of this investigation.
6. Trace the CRT error translation table contents and all fallback ranges in `Win32ErrorMapToErrno`.
7. Establish lifecycle for shared standard stream buffers at `DAT_005493e8`, including whether they are process-lifetime or freed at shutdown.
