# Finding 476 — Entity Activity and Runtime Records

This finding follows the activity and runtime-record procedures assigned in [issue #134](https://github.com/robbert229/lrr-portable/issues/134). Evidence is the checked-in pseudocode in [`LEGORR.full.c`](../decompiles/full/LEGORR.full.c) and its callers. Addresses identify procedures; descriptive labels are navigation aids. The observations below describe visible reads, writes, loops, and calls, without assigning undocumented meanings to numeric record kinds or flags.

## Activity records and state selection

`ActiveEntityListContainsCode @ 0x004031e0` searches the active selection when it is nonempty, otherwise the global entity list bounded by `DAT_004b3424`; each candidate is tested by `FUN_0044b480(candidate, argument)`. `EntityActivityRecordsRefresh @ 0x00403b60` acts only when entity word `+0x3e0` has `0x400` and lacks `0x2000`, then, for each entry counted at `+0x324` from `+0x308`, calls the activity-record remover for kinds 5, 6, 9, 15, 7, 4, and 20. `EntityActivityRecordRemoveByType @ 0x00403c00` finds the first matching kind in the linked list rooted at `+0x2f0`, performs kind-dependent cleanup, and unlinks/releases the matching record; a global bit-2 gate suppresses the operation. These calls show that refresh is selective list maintenance, not wholesale list reset.

`EntityActivityListRegister @ 0x00403f30` allocates kind `0xe` when the current head is absent or not kind `0xe`, linking the new record ahead of the previous head. `PendingTypeValueSlotSelect @ 0x00407a10` chooses a value from entity flags first, then walks past leading kind-`0xe` records and switches on the next record kind; several cases inspect nested record fields before selecting a `DAT_005578xx` value. This establishes a priority order in the code, while the user-facing meaning of those values remains unknown. `BubbleActionNameToIndex @ 0x00407300` scans a fixed name table case-insensitively; on a miss it returns the last comparison result rather than an explicit `-1` sentinel. `ResetObjectAuxiliaryState @ 0x00407370` clears `+0x388` and selects `+0x38c` only when its global enable is set.

## Terrain, steering, and other record consumers

`FUN_00409a40 @ 0x00409a40` iterates the counted entity slots at `+0x2c`, writes `-1.0` at each pointed record's `+0x340`, and sets bit `0x800000` at `+1000`. `EntityCellPathEffectsApply @ 0x00409d50` derives a direction from entity transform helpers, obtains cell-path records, updates the records and applies cell effects, conditionally builds a scene effect when entity byte `+0x3ec` bit 8 is clear, and finishes with `FUN_00409f20`. `EntityDestroyTrackedPointerCleanup @ 0x00409ff0` checks three global tracked pointers against flags from `FUN_00469e60`, replaces matching pointers using neighboring-object helpers, then calls two cleanup helpers. `TerrainCellEntityRecordUnlink @ 0x0040d100` returns a record to a global free-list head, clears two per-cell fields in the grid table, and invokes the cell update helper.

`DirectionDrivenHeadingAngleStep @ 0x0040f890` adjusts the angular value at `+0x28` toward either direction, clamps it to a global bound, or scales it near zero. `KindTwoSteeringTorqueApply @ 0x0040f920` normalizes vectors, derives a torque-like update from their alignment and object parameters, and updates fields `+0x30`, `+0x24`, and `+0x2c`. `SteeringPhysicsStep @ 0x0040fb90` forms a target displacement, invokes the two steering helpers and matrix composition, then updates position/velocity-like vector fields. The parameter and field names here are descriptive only; no unit or coordinate convention is established in this procedure.

`EntityPairCountRefresh @ 0x0041ec30` counts matching pairs in a global array and, if the count is nonzero, converts that count through two `__ftol` calls before invoking a refresh helper. `RemoveObjectIfClass6 @ 0x0041f840` calls `FUN_004489a0` only when `FUN_0044b480(object, 6)` succeeds, and always returns zero. `EntityEffectCountersApplyFromRecord @ 0x0042b2f0` checks bit 8 from `FUN_00469e60` and, when set, applies the two values at record offsets `+4` and `+8` through `FUN_0043a8f0` and `FUN_0043a910`.

`OListEntityRecordParse @ 0x0042e020` reads a structured object list. Per entry it reads `heading`, `health`, `driving`, and two additional numeric attributes; zero health is replaced with 100. It converts grid coordinates to world coordinates, resolves the named object through `FUN_0042e8b0`, creates the corresponding entity (with a separate path for kind 4), sets entity flags/fields, and retains the driving name and entity pointers in parallel arrays. A second pass case-insensitively matches those driving names, writes the matched entity pointer at `+0x2fc`, sets bit 4 in `+0x3e4`, and calls `FUN_0043f5b0` and `FUN_0043f100` to establish the relation. This is direct field-to-record flow; the meanings of the two additional attribute names and the complete relation semantics remain unresolved. `EntityPointer @ 0x0042ed70` maps integer kinds to fixed global objects or indexed arrays, writes the result through its output pointer, and returns success for recognized kinds; unknown-kind behavior is not a general pointer lookup contract. `FUN_004311d0 @ 0x004311d0` creates or updates a per-cell activity-build record when its third argument is nonzero, linking new records into the owner at `+0x88` and storing their pointer in the cell table. `FUN_004313b0 @ 0x004313b0` advances those linked records; based on scene completion and record flags it sets state bits or releases a record. `ActivityBuildRecordRelease @ 0x004314c0` releases the scene handle, clears the cell-table pointer, unlinks the record from the doubly linked list, and frees it. `ActivityBuildRecordsReleaseAll @ 0x00431530` walks that list and releases every record.

## Small field helpers and limits

`EntityB8Bit3SetOrClear @ 0x00435d91` sets or clears bit 3 of byte `+0xb8`. `RecordFields4And14Set @ 0x00435ef4` stores two supplied values at offsets `+4` and `+0x14`; `RecordField14Get @ 0x00435f0b` reads the latter. `EntityFieldsA0A4StoreA8Clear @ 0x00435f32` stores values at `+0xa0/+0xa4` and clears `+0xa8`.

The procedures cover several distinct record owners: entity activity lists (`+0x2f0`), scene-object cached handles, per-cell activity-build records, and global kind-specific registries. Their commonality is maintenance and lookup of runtime state, not evidence of one shared record type. Numeric kinds, flag meanings, and the complete `OListEntityRecordParse` schema remain focused follow-ups unless supported by separate field/caller evidence.
