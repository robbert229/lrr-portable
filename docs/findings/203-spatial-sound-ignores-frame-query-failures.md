# Finding 203 — Spatial Sound Ignores Frame-Query Failures

Both DirectSound spatial update paths consume Direct3DRM frame outputs without checking the frame-call results. The listener helper calls `GetScene`, `GetPosition`, and `GetOrientation`, then compares and may submit the returned vectors before committing deferred listener settings. The attached-source helper calls `GetScene` and `GetPosition`, then compares and may submit the result to the sound buffer and cache it. If one of these calls fails, the game still uses its output storage; the static evidence does not establish what values the Direct3DRM implementation leaves there on failure.

**Evidence.** Static disassembly of shipped `reference/LegoRR.exe`, SHA-256 `c3d8ce23f1aa21814950c77e713ec176599506d4e71758cf1cf709525e581e0f`. In `FUN_0047abc0` (`0x47abc0`), frame slots `+0x68`, `+0x60`, and `+0x7c` are called without testing their `HRESULT`s. The helper immediately compares the output vectors with cached listener state, passes changed values to listener slots `+0x38`/`+0x34`, updates its caches, and may call `CommitDeferredSettings`; finding 196 maps these frame calls and vectors. In `FUN_0047b410` (`0x47b410`), slots `+0x68` and `+0x60` are likewise called without checking their return values; the returned position is compared with the per-source cache and, if different, sent to buffer slot `+0x4c` and copied into that cache, as detailed in findings 162 and 198. The call sequence is in `docs/decompiles/full/LEGORR.full.c` and the shipped binary.

This is a conditional error-path observation, not evidence that Direct3DRM frame queries fail in ordinary gameplay.
