# Finding 162 — Object-Attached Sounds Refresh Spatial State

The object route used by `FUN_00465090` can attach a playing sound buffer to a game object that exposes spatial state. In `FUN_0047ad70`, the object-attached branch registers the buffer through `FUN_0047b1a0`. That helper retains the object in a fixed 20-entry registry and creates a record linked to the object's own list. The sound update path later visits each registered object and its linked sound records.

`FUN_0047b390` walks the registry and calls `FUN_0047b410` for each non-null frame. The latter calls the frame's `GetScene`, then calls `GetPosition` relative to that scene. It compares the resulting three floats with the last values stored for each linked sound record, and calls the associated buffer's vtable slot `+0x4c` (`SetPosition`) with apply flag `0` when they change. DirectSound defines `0` as immediate application. The helper then stores the new values. The routine is reached by the recurring sound update path at the end of `FUN_004651a0`.

At initial object-route registration, `FUN_0047ad70` also queries the frame's scene-relative position, but passes apply flag `1` to the buffer setter. The same dispatch then reaches listener slot `+0x44` (`CommitDeferredSettings`) before returning. This initial deferred write is committed in that dispatch; later per-tick refreshes use immediate application.

This establishes that the object-attached route refreshes each attached source from its frame position relative to its scene, then submits that position without coordinate conversion. Direct3DRM positions are unitless, as described in finding 196; DirectSound interprets a vector unit as one meter by default, as documented in finding 199. Finding 198 records the conditional cache behavior if a source-position update fails. Finding 165 documents the registry's capacity and insertion behavior. Finding 161 documents gameplay callers on the object-attached route; finding 121 documents the 3D-control flag on loaded per-source buffers.

**Evidence.** Static decompile and disassembly of shipped `LegoRR.exe`, SHA-256 `c3d8ce23f1aa21814950c77e713ec176599506d4e71758cf1cf709525e581e0f`, in `docs/decompiles/full/LEGORR.full.c`: `FUN_00465090` at `0x465090` selects the object route; `FUN_0047ad70` at `0x47ad70` registers its associated buffer; `FUN_0047b1a0` at `0x47b1a0` creates the registration and linked record; `FUN_0047b390` at `0x47b390` and `FUN_0047b410` at `0x47b410` refresh changed values. In `FUN_0047b410`, the frame vtable calls at `+0x68` and `+0x60` are followed by a buffer call at `+0x4c` with final argument `0`, then the queried values are copied into the cache. In `FUN_0047ad70`, the initial object route calls `SetPosition` at `0x47af2e` with final argument `1`, and common cleanup calls listener `CommitDeferredSettings` at `0x47afb5`. `FUN_004651a0` at `0x4651a0` reaches the update path. These are static call and data-flow observations, not runtime measurements.
