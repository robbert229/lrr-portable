Refs #442 #443 #444 #445. Stage S3 of the [#388 plan](../plans/388-original-link-order.md),
[ADR 0006](../adr/0006-original-link-order.md) decisions 3–4 and entropy
rules 2–3. This is the first relocation wave after #506
([finding 541](541-per-relocation-private-headers.md)), which gave each
relocation its own frozen `<l>_for_<u>.hpp` / `<l>_from_<u>.hpp` pair.
Measured on `main` `c155edab`, after #509 (GAME-016 converted) and #507
(reshapes). The first run, on `8e8d4da3`, was reset onto that `main` and the
tool rerun. It regenerated byte-identical unit files and private headers, and
changed the same five listings.

## Summary

1. **Three units move**, one tool-generated commit each, in link order, with
   no hand edits and no fix-ups: GAME-011 (R1, the last plain R1 unit), GAME-018
   (HelpWindow.c, R3) and GAME-022 (R4). Together they move 56 functions, 13
   owned globals and 24 closure items into three new unit files.
2. **G98-009 does not move.** Its declaration split is refused before it
   writes anything, because the relocation it plans hits a conditional group in
   `src/gods98/sound.cpp` (below). The split step plans the whole relocation
   first, so there is no split commit to make. G98-009 waits for #501
   (conditional groups).
3. **No previously relocated unit's listing changed.** None of the 53 existing
   unit files and none of their private headers is edited. All 726 of their
   functions in the report keep identical listing digests in both scopes. That
   includes operand labels: unlike finding 541's replay, no label changed here.
4. **Five listings change**: two in moved code and three in the legacy files
   the units left (`frontend.cpp`, `view.cpp`). Only one score drops:
   `0x004882e0` falls 12.13% → 12.11% and gains one instruction. **No exact
   match is lost**, exact-function code bytes are unchanged (65,713), and the
   means stay at 56.34% full and 51.65% game-only.
5. **Layout:** pair inversions fall from 320,874 to 292,291 (−28,583), and unit
   contiguity rises from 83.56% (183 units) to 84.93% (186).

## G98-009: blocked by a conditional group

On `main`, the survey reports G98-009 as needing `--split-declarations` only
(`simtick.cpp:413`, `static int s_sound_on, s_sound_active;`). Running
`relocate_unit.py G98-009 --stem sound3d --split-declarations --check-layout`
refuses before it writes anything:

```
refused: G98-009:
  - src/gods98/sound.cpp:1011 (sound_frame_release): inside an #if block
  - src/gods98/sound.cpp:1057 (sound_frame_release): inside an #if block
  ... sound_frame_scene_get, sound_frame_position_get, sound_buffer_position_set
```

- **The construct.** `sound.cpp:986–1066` is one `#if MSVC/x86 … #elif
  GNU/i386 … #endif` group. Each branch defines four `static` COM-call helpers:
  `__asm` in the MSVC branch, `thiscall` function-pointer calls in the GNU
  branch. The GNU branch also holds four `typedef`s.
- **Why the tool refuses it.** It accepts a group only when each branch holds
  one whole definition of the same function. The split step plans the whole
  relocation first, so the split is never written.
- **Why the survey missed it.** For a unit that only needs a split, the survey
  reports the split refusal alone. The `#if` refusal only appears after the
  split is planned. Finding 537 had already noted this ("its split works;
  next, `#if` blocks in `sound.cpp`").
- **Paths forward.**
  - #501 moves top-level conditional groups whole.
  - A reshape under the ADR 0006 addendum is also possible: four
    one-function groups, with the GNU-only `typedef`s hoisted into their own
    group. The relocation tool would still refuse that hoisted group until
    #501 lands.
  - This PR does neither: it does not modify `relocate_unit.py` and makes no
    reshape.
