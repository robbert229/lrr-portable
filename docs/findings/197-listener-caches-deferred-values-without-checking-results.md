# Finding 197 — Listener Caches Deferred Values Without Checking Results

`FUN_0047abc0` submits changed listener position and orientation through DirectSound with the deferred-apply flag, then copies the requested values into its comparison cache. It later calls `CommitDeferredSettings`. None of these three HRESULTs is checked. On the next update, the helper compares new frame vectors against the cache and skips setters when they are unchanged.

If a position or orientation setter fails, the helper has already marked that vector as current, so it will not retry the failed update until the provider vector changes. If the deferred commit does not succeed, the same cache also suppresses another setter/commit cycle while the vectors remain unchanged. This is a conditional failure-path hazard; static analysis does not establish that any of these calls fail in normal gameplay or that a particular listener state is reached.

**Evidence.** Static disassembly of shipped `reference/LegoRR.exe`, SHA-256 `c3d8ce23f1aa21814950c77e713ec176599506d4e71758cf1cf709525e581e0f`: in `FUN_0047abc0` at `0x47abc0`, listener vtable slot `+0x38` (position) is called at `0x47ac15`, then the three position values are stored at `0x47ac24–0x47ac2f`; slot `+0x34` (orientation) is called at `0x47aca3`, then six orientation values are stored at `0x47acb2–0x47acda`; slot `+0x44` (deferred commit) is called at `0x47acef`. The call results are not tested. The following invocation compares against those caches and avoids setters for identical values (finding 163). Microsoft documents that listener setters return HRESULTs and may fail, and that deferred updates are applied by `CommitDeferredSettings`: [SetPosition](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418028%28v%3Dvs.85%29), [SetOrientation](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418026%28v%3Dvs.85%29), and [CommitDeferredSettings](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418006%28v%3Dvs.85%29).
