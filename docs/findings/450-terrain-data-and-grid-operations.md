# 450 — Terrain data and grid operations connect map cells, surface state, and terrain queries

*Target: `LegoRR.exe` (SHA-256 `c3d8ce23f1aa21814950c77e713ec176599506d4e71758cf1cf709525e581e0f`), Ghidra 12.1.4 via REA.*

This finding maps the 54 functions assigned to `terrain-data-grid`. They form a terrain context around a row-major table of `width * height` cell records (0x28 bytes each), plus geometry/surface state and several temporary work queues. The evidence supports describing concrete data flow and call relationships; several short helper names remain inferred, and the decompiler does not establish the game's higher-level intent for every flag or field.

## Construction and cell state

`TerrainCreate` (`0044e0c0`) reads map dimensions and terrain parameters, allocates the context and cell table, initializes cell attributes (`+0x19 = 0x60`), copies the map cell value into `+0x1a`, builds per-cell geometry, and chooses a diagonal from corner-height differences. `TerrainGridVertexBuild` (`0044e4d0`) emits four vertices per cell from grid position, scale/origin, corner offsets, and the height byte, then submits the quad to the geometry buffer. The layout and height use are detailed in findings 54 and 114. `MapFileReadHeader` (`004515a0`) reads width/height from the map header; `MapFileGetCell` (`004515c0`) reads a 16-bit row-major entry at map offset `+0x10` and does not check coordinates against the dimensions.

`TerrainGridCellsInitialize` (`0044e880`) walks the grid and invokes the per-cell initializer `FUN_00450f30`. The routine builds four corner coordinates in the order `(x,y)`, `(x-1,y)`, `(x-1,y-1)`, `(x,y-1)`, samples one three-float vector for each through `TerrainCellNormalSample` (`004512d0`), then computes four output vectors. For each output it visits those four samples, calls `CellVariantEntryMatchCheck` (`00451180`) with the output corner and sample-cell coordinates, and accumulates the sample only when that helper returns zero. It normalizes each accumulated vector by its Euclidean length and writes it through `TerrainCellSurfaceVectorWrite` (`00451230`). That writer rotates the destination corner index by one when the cell orientation bit is set, then updates the cell's geometry surface-vector field. `TerrainCellNormalSample` returns a zero vector for out-of-bounds samples and combines the cell's two stored vector fields for the two diagonal corner indices. `TerrainCellSurfaceVectorOffsetAdd` (`00451450`) adds an offset vector to a selected cell corner. `TerrainCellSurfaceVectorsRebuild` (`004514f0`) rebuilds the cell's stored surface-vector sets from its four corners. These are observed vector operations; the evidence does not justify assigning every vector a more specific normal/lighting meaning.

### Per-cell surface-vector initializer (`FUN_00450f30`)

The binary at `0x450f30` matches the checked-in Ghidra pseudocode: it contains the four-sample setup, nested four-iteration accumulation, square-root normalization, and four calls to the surface-vector writer. Caller evidence shows `TerrainGridCellsInitialize` traversing every `(x,y)` cell and passing the coordinates to this routine (REA Evidence `ev_69fcfae5b26c15d810f32f8ed1bb85b09bc4e84c49f617200767116102d47d36`); the dirty-cell update path also calls it for cells with the refresh bit set, then clears that bit (REA Evidence `ev_9b9ca65c48201b3ff98024ab5b4211b5dcbbd0976ca036197b6dfe46a1aed1fb`). No retained REA record directly analyzes `0x450f30`; its operation details here come from the checked-in Ghidra pseudocode, corroborated by local `objdump` of the digest-matched executable. This supports the operation-level name **`TerrainCellSurfaceVectorsInitialize`** as a candidate. It is not yet recorded as an established corpus name.

`CellVariantEntryMatchCheck` returns 1 when the second cell's material byte appears in the first material's configured byte list, after bounds and sentinel checks. The initializer accumulates only on a zero result, so the configured match excludes that sample from the output sum. The evidence establishes this branch behavior, but not why the table defines those pairs or the game's higher-level material semantics. The normalization has no zero-length guard in the disassembly; static evidence alone does not establish whether a zero sum can occur on shipped maps or what runtime consequence it has.

`TerrainCellOrientationToggleAndRebuild` (`0044edf0`) changes the cell orientation bit, rotates four corner blocks, rebuilds the surface vectors, and marks adjacent cells for refresh. `TerrainCellChangedFlagSet` (`0044efb0`) sets a per-cell refresh bit and the terrain-wide dirty bit. `TerrainDirtyCellUpdate` (`0044eff0`) scans dirty cells and reinitializes them, then advances the terrain animation and material-transition handlers. `FUN_0044f090` advances the ten-record material transition pool, updating cell geometry over time and restoring/deactivating completed records. `TerrainCellMaterialTransitionBegin` (`0044e6d0`) captures previous geometry/material state in an available transition record and calls `TerrainCellMaterialSet` (`0044f230`); the setter bounds-checks, updates the cell's material byte and mesh material, and refreshes corner data except when the cell's suppression flag is set. `GridCellSetPayloadIndex` (`0044e860`) forwards a row-major cell index to the geometry setter.

`TerrainCellSurfaceTypeSet/Get/Reset` (`0044f4e0`, `0044f540`, `0044f570`) write/read/reset a separate byte at cell offset `+0x24`; the setter applies the corresponding appearance table. `TerrainCellSurfaceAppearanceApply` (`0044f5c0`) either applies the selected appearance or resets it and clears the stored type. The meaning of the surface-type byte is not established here. `NestedPointerRecordDestroy` (`0044e670`) releases the context's nested allocations and the context. `IndexedFlagValueSetOne` (`0044e6b0`) stores one in a byte-indexed flag array. `SceneObjectResourceHandleSet` (`0044f220`) writes a resource handle at object offset `+0x2c`. `InputKeyMappingAddBidirectional` (`0044f1a0`) adds two byte values to reciprocal fixed-stride mapping tables; its placement in this address range does not show that it is terrain-specific.

## Mutations and deferred work

`TerrainCellListSurfaceHeightClampMutate` (`0044ead0`) stages distinct consecutive coordinate pairs, reads each cell's four corner heights, partitions corners using a cell flag, computes an average, clamps selected heights within a tolerance band, then calls `TerrainVoxelNeighborsMutate` (`0044f380`) and marks processed cells. The neighbor mutator adjusts the selected cell's corner vectors and rebuilds the surrounding 2×2 cells' surface vectors. `SurfaceVertexSpanValidate` (`0044e8c0`) validates a coordinate-pair list against per-segment gradient and aggregate height-span limits; exact semantic names for its numeric parameters are not recoverable from the call body alone.

`GridSurfaceWriteAtXY` (`00450700`) writes a surface value at a row-major cell index. `TerrainCellChangeQueueAppend` (`00450730`) writes value 0 immediately and appends the coordinate pair; `TerrainCellChangeQueueFlush` (`00450780`) replays each queued coordinate with value 1, then clears the count. `CellDirtyQueuePushAndClear` (`00450960`) adds/removes cell coordinates from a terrain-owned queue and sets/clears a cell state bit. `CellListMinDistanceScaleApply` (`00450a80`) applies or clears three scale channels for cells in a stored list, subject to a context flag. `FUN_00450b60` interpolates listed cell vertex data over time, applies a small perturbation, and updates geometry when its time parameter passes a threshold; dirty-list processing calls it from `TerrainDirtyCellUpdate` (`0044eff0`). `CellNeighborDirectionCode` (`004508a0`) maps an adjacent coordinate pair to one of eight direction codes and returns -1 for non-neighbors. `TerrainCellEdgeVectorQuery` (`004507d0`) selects an edge vector based on neighboring coordinates. `FUN_00450890` (`00450890`) returns the terrain scale stored in the context. `FUN_00450600` (`00450600`) scans a circle of the supplied radius around a cell, clears each in-bounds cell's surface value through `GridSurfaceWriteAtXY`, optionally calls a per-cell callback, and records visited coordinates in a context list.

## Coordinate conversion and queries

`MapCellToWorldCenter` (`0044f640`) bounds-checks a cell and returns its world-space center. `WorldToTerrainCellBoundsCheck` (`0044f700`) converts world coordinates to integer cell coordinates and local fractions, succeeding only inside the grid; `TerrainGridPick` (`0044f6d0`) adapts that query. `GridCoordinateClampAndStore` (`0044f810`) converts and clamps coordinates to valid grid limits. `TerrainWorldPointToCell` (`0044f870`) returns cell coordinates and optional local offsets. `TerrainSurfaceHeightInterpolate` (`0044f940`) picks a cell and interpolates height across the triangle selected by its diagonal. `TerrainCellSurfaceTriangleVerticesSelect` (`0044fab0`) returns the corresponding triangle's vertices based on orientation and local position. `TerrainSurfacePointProjectOffset` (`0044fb90`) projects a point against the selected cell surface. `FUN_0044fe70` (`0044fe70`) calls `TerrainGridPick` (`0044f6d0`), reads the four cell corner heights, forms corner positions, selects the diagonal triangle, and interpolates a surface height; it returns zero if the pick fails.

`GridCellReadSurfaceVector` (`00450060`) reads one selected corner vector; `TerrainCellSurfaceVerticesGet` (`004500d0`) retrieves the cell's four surface vertices; and `GridCellReadSurfaceValues` (`00450220`) copies the selected surface-value block. `CoordinatePairWithinBounds` (`004502c0`) checks both coordinates against supplied bounds. `ScreenRayTerrainCellPick` (`004502e0`) routes a camera/view ray through map-coordinate selection and terrain ray testing. `RandomReachableGridPointSelect` (`00450560`) samples grid positions until the associated reachability check succeeds or its retry limit is reached. `GridCellOperationApplyAll` (`0044f490`) iterates the terrain dimensions and applies the supplied operation to each row-major cell.

## Data flow and limits

The principal path is map header/cell data → `TerrainCreate` cell records → geometry and per-cell surface vectors → mutation/dirty queues → rebuild and geometry updates. Coordinate queries share the same dimensions, scale, origin, cell table, and diagonal state, while screen picking adds camera-ray input. Existing findings cover specific slices: [54](54-terrain-grid-emits-per-cell-quad-vertices.md), [55](55-terrain-cell-material-changes-use-bounded-transition-records.md), [114](114-terrain-cell-height-and-diagonal-selection.md), [242](242-path-step-terrain-and-pending-record-helpers.md), [374](374-terrain-interface-and-media-helpers.md), [375](375-entity-ui-and-render-tree-helpers.md), [386](386-spatial-ui-com-and-crt-runtime.md), and [410](410-map-and-visual-resource-records.md).

The map accessor and several query helpers rely on callers to supply sensible context/pointers; only some perform coordinate bounds checks. This is static analysis of the shipped executable. It does not establish runtime behavior or all meanings of cell flags. Focused follow-up tickets could resolve those helper contracts and audit the boundary behavior of the map accessor and queued mutation paths.
