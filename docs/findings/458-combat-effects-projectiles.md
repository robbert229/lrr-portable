# Finding 458 — Combat Effects and Projectiles

The assigned 18 functions form three connected paths: effect-hit dispatch, persistent projectile/flight records updated during a frame, and surface/segment collision plus transient segment visuals. The observations below come from the checked-in decompile [`LEGORR.full.c`](../decompiles/full/LEGORR.full.c); names for anonymous helpers remain provisional and numeric kinds/flags are left literal where their meanings are not established. Findings 247–249, 258, 285, 401, and 433 already document several individual helpers; this finding ties their state and caller flow together.

## Hit response and motion

`TypeMotionScaleApplyDispatch @ 0x0046f270` reads a type-indexed value through `FUN_0046f1d0`, which uses the selected entity record and falls back to a per-type default when the configured field is `-1`. It proceeds only when entity flag `0x40000` is set and `FUN_004385b0(entity, 1)` succeeds. A per-type mode field at `DAT_00503878 + type*0x4b68 + 0x4b00` selects either a scaled impulse plus entity type/index stores and `FUN_00447950`, or a direct scaled impulse; for type 3 the latter path increments a global float counter. The exact physics meaning of the fields and mode is unresolved.

`EntityApplyImpulseAndDirection @ 0x0046f380` is a thin relay to `FUN_0043f6a0(entity, impulse, 1, 1.0)` followed by `FUN_00447950(entity, 0, direction)`. `EffectApplyByKindBranch @ 0x0046f770` first runs `FUN_004436f0` and conditionally clears a supplied state through `FUN_0040be10`, then selects one of three state-flag-gated responses: kind 1 checks `0x02000000`, applies an impulse, and requests effect selector 0; kind 2 checks `0x04000000`, scales a position pair by 1.5, applies impulse and pair/scalar state, and requests selector 1; kind 3 checks `0x01000000`, uses offset `+0x10c` as a positive scale or 10.0 fallback, applies an impulse and a separate effect helper, and requests selector 2. Other kinds call `TypeMotionScaleApplyDispatch`. `RayHitScanAndEffectApply @ 0x0046f3b0` is the observed caller of this dispatch. Findings 258 and 433 trace the associated attachment helpers; the numeric flag semantics are not inferred here.

## Ray scan and persistent records

`RayHitScanAndEffectApply @ 0x0046f3b0` operates when the owner record at `+0x2a4` is non-null. It checks range from the ray origin (`+0x274..+0x27c`) using `FUN_0046f170(+0x2a8)`; an out-of-range record is released with `FUN_00437540` and its slot cleared. Otherwise it builds a ray from the origin toward `+0x280..+0x288`, calls the entity/cell scan callbacks (`LAB_00471370`, `FUN_00471630`), and on a hit releases the previous tracked entity. When the scan result contains an entity, the hit point is interpolated from the ray data and passed to `EffectApplyByKindBranch` with owner values `+0x290`, `+0x2a8`, and `+0x2ac`. `FUN_0046f550` is the sole caller in this area and runs the per-frame work.

`FUN_0046f550 @ 0x0046f550` walks the fixed-stride active spawn/projectile records and calls `FUN_0046f920` for occupied slots, runs the segment-ray callback `LAB_0046f610`, then calls `RayHitScanAndEffectApply` for every record. It also walks a second fixed-stride timed-visual table, releases its two handles when its timer is negative, clears the slot, and subtracts frame delta from active timers. The table bounds/strides are visible in the loop; lifetime ownership beyond those releases is not fully established.

`FUN_0046f920 @ 0x0046f920` advances an occupied record by `frameDelta * speed`. Mode 0 linearly advances position by stored velocity; the other mode advances a curve parameter and evaluates the curve through `FUN_004068c0`. It updates the associated scene handle through `FUN_00475430` and applies a fixed orientation through `FUN_00475470`.

`EntitySpawnRecordSlotInit @ 0x0046faf0` maps request kinds 1–4 through `EffectModeSurfaceQueryTypeResolve`, validates the resulting surface pair, claims a free slot using `ActiveEffectRecordSlotFind`, writes start position, normalized direction, speed 5.0, object/owner values, creates an entity with `FUN_00438610`, and registers it in the active record. Kind 1 first calls `FUN_00437300(param1, param4, 1.0)`. `ObjectFlightCurveRecordInit @ 0x0046fc70` uses the same slot family: it stores start and end positions and normalized direction, chooses speed 4.0, builds a 50-sample curve with control offsets derived from 20% and one-third of the distance, creates the entity, and registers the record. The callers and field-level details are also in Findings 247, 248, and 256.

`EffectModeSurfaceQueryTypeResolve @ 0x0046fef0` maps kinds 1, 2, 3, and 4 to query pairs `(0x13,0)`, `(0x10,0)`, `(0x11,0)`, and `(5,0)`; other values leave outputs unchanged. `ActiveEffectRecordSlotFind @ 0x0046ff70` scans the fixed-stride record table for the first zero owner/entity slot and returns its index, or `-1` when full. `ActiveSegmentVisualRecordSlotFind @ 0x0046ff90` does the same for the timed visual table.

## Spatial impact and segment visuals

`LaserSpatialSoundAndImpact @ 0x0046ffb0` emits spatial sound selector `0x1b`, casts a segment through `FUN_00471860`, computes its endpoint, and creates a timed segment visual. If an entity is hit, it emits the impact effect and selector `0x1c`, then applies direction/impulse; otherwise it resolves a terrain cell and uses per-type range plus cell surface type to select a terrain impact path, with a separate fallback when the position is outside the normal cell lookup. It finishes by calling `FUN_00437300` with the request entity/type and supplied scale. Exact sound names and surface-type semantics are unresolved.

`EntitySurfaceSegmentCollisionCheck @ 0x00470260` branches on entity-record bit `0x100`: set selects `EntitySurfaceQuadSegmentIntersect`, clear selects `SegmentCenterProximityCheck`. The quad path `@ 0x004702b0` can reject a segment by `EntityDirectedLineSideCheck`, transforms the four corners of the entity rectangle using the object transform, and tests the segment against each edge, optionally returning the intersection point. The proximity path `@ 0x00470540` can apply the same directed-side rejection, finds the segment midpoint, transforms the entity center, and compares their distance with the field returned by `NestedFloatAtOffset6CGet`. `EntityDirectedLineSideCheck @ 0x00470630` returns whether the dot product between entity-center displacement and the supplied direction is negative. Caller `CellSightRayCheckAndFlag @ 0x00466490` calls the dispatcher with a zeroed optional-side-check argument (see `LEGORR.full.c`); the broader interaction path is also described in Finding 285.

`TimedEntitySegmentVisualCreate @ 0x00470690` claims a free timed-visual slot, creates two mode-`0x4400` visual handles, builds both with the same endpoints but different widths/colors, and stores the owner plus a 5-second lifetime. `MeshBuildEightSidedSegment @ 0x00470760` constructs and submits the segmented mesh data for one such visual handle; the eight-sided name reflects the repeated vertex/face construction, while the visual's domain identity is not proved. Findings 285 and 401 record the two-buffer creation and release path.

## Limits and follow-up

The decompile establishes control flow, fixed strides, field offsets, branch constants, and helper calls. It does not identify all effect kinds/flags, the precise physical meanings of the per-type configuration fields, the complete callback filtering rules behind the ray sweep, or all resource ownership outside the visible release paths. Existing findings already cover the concrete slot initialization, ray scan, collision, and visual mesh slices, so no duplicate implementation ticket is warranted from this pass. A focused follow-up would be useful if later work can recover source data or runtime evidence for the numeric effect kinds and per-type mode table; static decompilation alone does not resolve those semantics.
