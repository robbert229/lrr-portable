# Finding 171 — Queued Shared-Object Sound Stores Handle Zero

The `SharedObjects` sample callback uses `FUN_00465090(object, alias, changed, 1, 0)`. When the sound batching flag (`DAT_00502a2c & 8`) is set, `FUN_00465090` puts the request in its ten-entry deferred queue and returns `0`; the queued path does not return a playback handle. `FUN_00487de0` nevertheless stores that return value in the event's handle field.

If the changed-event stop branch then runs, it passes the stored zero to `FUN_0047b130`. The handle decoder `FUN_0047b0f0` treats zero as buffer slot zero (`(handle - handle % 3) / 3 == 0`, variant `handle % 3 == 0`), and the stop helper calls that buffer's stop vtable method when the sound system is on and the slot pointer is non-null. Thus a queued transition can target slot zero instead of a handle returned by the queued request. The deferred queue later submits the request separately, so its eventual handle is not associated with this event record.

This is conditional code behavior. The static evidence does not establish that the batching flag is set during a shipped `SharedObjects` event update, or that slot zero is occupied at that moment. Finding 170 documents the separate immediate-mode case where a new callback handle overwrites the prior event handle before the stop call.

**Evidence.** Shipped `reference/LegoRR.exe`, SHA-256 `c3d8ce23f1aa21814950c77e713ec176599506d4e71758cf1cf709525e581e0f`. `FUN_00487de0` at `0x487de0` stores the result of the registered submission callback and later calls `FUN_0047b130` with the stored value. The callback is registered as `FUN_00465090` by `FUN_004876c0` at `0x4876c0`; its batching branch queues the request and returns zero at `0x465090`. `FUN_004652d0` at `0x4652d0` later drains queued requests. Handle decoding and stop are in `FUN_0047b0f0`/`FUN_0047b130` at `0x47b0f0`/`0x47b130`. The decompilation is in `docs/decompiles/full/LEGORR.full.c`; queue semantics and capacity are also covered by findings 139 and 149.
