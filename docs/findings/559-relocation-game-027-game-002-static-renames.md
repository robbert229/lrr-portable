## `reshape_check.py --rename OLD=NEW`

A rename changes one token, so `reshape_check` reports differences in the
token streams, the `.text` relocations and the symbol table, even when
nothing else changed. Finding 548 read such a result for `cmd.cpp` as
"relocations and the symbol table differ by name only". That reading missed
a moved `.bss` symbol: the symbol-table check compares values too.

`--rename OLD=NEW` (repeatable) spells the base's tokens, relocation targets
and COFF symbol names with the new name, then compares as usual. A name is
matched whole within MSVC's decorations:
- plain `old` and C `_old`;
- a file static's `_old$S46642`;
- C++ `?old@@3HA`, or a scope `?f@old@@`.

Symbol values and order still count, so a rename that moves `.bss` still
fails. Fixture tests are in `tools/tests/test_reshape_check.py`. Commit
`2cd30549`.

## The renames

### `cmd.cpp`: `s_queue_count` → `s_queued_count`

`info.cpp` defines `s_queue_count` too (`0x004dcd38`).

The first name tried, `s_cmd_queue_count`, gives the same `.text` bytes but
not the same `.bss` layout: the array moves from the end of `cmd.obj`'s
hashed run (offset `0x1b430`) to its start (`0x18ba8`), and the 27 other
statics before it shift by 8 bytes. `s_queued_count` keeps every offset:

```
$ python3 tools/reshape_check.py src/game/cmd.cpp --rename s_queue_count=s_queued_count
src/game/cmd.cpp:
  rename: s_queue_count -> s_queued_count (base spelled as head)
  includes: identical
  native: identical
  matching: identical
  mingw: identical (emulated: host gcc + reference defines)
  object: identical (including .drectve when present)
```

### `ai.cpp`: `s_active_count` → `s_active_list_used`

`sfx.cpp` defines `s_active_count` too (`0x00502bd4`), and frozen private
headers name it. Several obvious names reorder `.bss`, among them
`s_ai_active_count`, `s_active_entity_count` and
`s_active_entity_list_count`. `s_active_list_used` keeps every offset:

```
$ python3 tools/reshape_check.py src/game/ai.cpp --rename s_active_count=s_active_list_used
src/game/ai.cpp:
  rename: s_active_count -> s_active_list_used (base spelled as head)
  includes: identical
  native: identical
  matching: identical
  mingw: identical (emulated: host gcc + reference defines)
  object: identical (including .drectve when present)
```

Neither rename is a reshape under the ADR 0006 addendum, which allows
renaming only file-local macros. Each is a fix commit under rule 3, with its
own proof.

### How MSVC 5.0 orders `.bss` statics

Test objects were compiled with `cmd.cpp`'s matching command line. Finding
512 said only "by name hash"; these measurements say more:

- Uninitialised `static` data, and uninitialised external data, form one run
  in **ascending order of a name key**. When two names have equal keys, the
  later declaration comes first.
  - All 52 one-letter names come out in character order.
  - Two-letter names follow `4·c1 + c2`: `ba` and `ae` tie, and `ba` comes
    first.
  - Three-letter names follow `16·c1 + 4·c2 + c3`.
- From about six characters on, the high bits fold back into the key. Over
  the last character, the key behaves like `(B + c) ^ F`, where `B` and `F`
  come from the prefix. The fold itself was not identified: none of the
  shift, rotate, mask, modulus or ELF-style fold families tested fits every
  sample.
- In `cmd.obj`, the zero-initialised statics checked (`s_block_live = { 0 }`,
  `s_global_head` and `s_global_tail = NULL`, `s_keybind_count = 0`) follow
  the hashed run, not inside it.

Without the formula, a search is cheap. The search compiles the real file
once per candidate, eight at a time; a `cmd.cpp` compile takes well under a
second. It keeps candidates whose object is identical modulo the rename.
The search scripts were throwaway and are not committed. The method is: a
list of candidate names, then `reshape_check.compare_objects(base,
candidate, renames={old: new})` on each compiled object.

After relocation, both variables leave their legacy files. The name choice
only makes the fix commit itself zero drift. In the unit files, their
`.bss` neighbours are new anyway.

**Flagged for the owner (rule 2):**
- both falls. They have one cause, the one behind finding 552's
  `0x0041c4f0`: external linkage changes MSVC 5.0's code for the moved
  functions' data accesses. Neither recomp size changes; registers,
  scheduling and branch layout do.
- Avoiding the export means moving `cmd_context_set` and
  `cmd_queue_active_count_peek` (port-only, unannotated) and `cmd.cpp`'s
  pool users out of `cmd.cpp`. That is a hand edit beyond the tool. It is
  left for the conversions, which own these units' data shapes.
