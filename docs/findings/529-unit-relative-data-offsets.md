# Finding 529 — Unit-relative data gaps and anchored offsets

Issue #450, stage S6c of [the link-order plan](../plans/388-original-link-order.md). Measured after R1 merged, using the matching build of this tree (`make reccmp-check`, then `make match-progress`). Run `make unit-data-offsets` to reproduce. The table covers all rows of the unit-range CSV, including CRT rows; a unit's classification is partial if any section mismatches, otherwise n/a if an active section is unresolved, otherwise gaps-only or full. The summary is **0 full, 1 gaps-only, 6 partial, 218 n/a**. This does not imply the 218 disagree: most lack attributable pairs or a dedicated object. Unowned/ambiguous addresses are reported by the command.

For each original section the tool compares gaps from the first attributable annotated item; an unassociated annotation prevents a full or gaps-only result. Where finding 524 supports an original `.rdata` start it also checks the absolute offsets. A partial result reports the number of mismatches and first original address followed by original/rebuilt gap or anchor offsets in hex; negative offsets mean rebuilt order is reversed. Counts are attributable items and unknown annotations. `n/a` includes fewer than two attributable items and unavailable objects. `-` means no common was identified; detected commons include their original address, COFF name and size. This is a source/COFF model, not a claim about final linked placement; `$` sections and COMDAT pieces are laid out in COFF order with their recorded alignment. Reccmp entity addresses and map symbol names resolve literals in the linked object; strings and globals that cannot be mapped unambiguously are unknown. The map establishes linked objects and the current CMake link response selects them over stale object files. Original ranges are evidence ranges, and the tool reports addresses outside or overlapping them separately.

GAME-003's three `.rdata` gaps agree, but the anchor offsets are `14/18/1c` original versus `0/4/8` rebuilt. The 20-byte prefix is likely the four Direct3DRM constants and the intervening 4-byte value documented in finding 524. Its `bezier.c` does not include `d3drm.h`, and the compiled object contains no `{1,2,4,-1}` byte sequence. G98-019 likewise has four matching gaps but its absolute offsets are all `0x10` early; `draw.c.obj` also has no such sequence. G98-006 and G98-007 show the same anchored-prefix discrepancy. Finding 524's attributions are inferred from references and order, not an original map.

GAME-001's `.bss` has nine gap mismatches among ten attributable annotations, beginning at `004b2e04`; GAME-015 has both `.rdata` and `.bss` gap mismatches, among 13 attributable `.bss` annotations. GAME-014's two attributable `.bss` items have matching gaps, but its two unresolved `.data` annotations prevent a unit-wide result. G98-018 has 101 matching `.data` gaps and no other active ordinary section, giving one gaps-only unit. G98-027 has 331 matching `.data` gaps but only one `.bss` item, so its unit status is n/a. The common bucket identifies `_key_names` (1028 bytes in this rebuild) and `_sound_mci_return` (200 bytes); finding 525 explains why their allocation is not scored as ordinary per-object `.bss`.

For relocation waves, correct link order alone cannot restore missing header prefixes or within-unit data shape. The anchored results identify concrete follow-up work for converted units, while the unresolved cases need relocation, symbol attribution and evidence for original ownership before claiming full agreement. Commons require the separate COFF allocation treatment in finding 525. The check is a diagnostic and does not modify the binary-progress baseline.
