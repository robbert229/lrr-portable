# Finding 460 — Velocity and Collision Queries

The assigned functions form two related paths: entity-owned velocity slots that blend/steer scene objects, and segment/radius queries that test those objects against terrain or other entities. Direct mechanics below are visible in the checked-in decompile [`LEGORR.full.c`](../decompiles/full/LEGORR.full.c). Findings 247, 256, 258, 294, 285, and 357 already describe some of the callers and sweep helpers; this finding connects the slot layout, dispatch gates, and query outcomes while retaining unresolved flag and vector semantics.

## Velocity-slot records and steering

`EntityVelocityStateRecordGet @ 0x004712c0` selects the velocity-state record by entity kind: kind 1 returns `param[3] + 0x138`, kind 4 returns `param[6] + 0xa0`, and other kinds return null. `EntityVelocitySlotValueGet @ 0x004712f0` and `EntityVelocitySlotValueSet @ 0x00471310` read/write float slot `record + 0x98 + index*4`. `ReadIndexedPairSlotDword @ 0x00471a20` is a generic dword reader at `base + pairIndex*8 + fieldIndex*4`; `VelocitySlotPrimaryObjectGet @ 0x00471a40` and `VelocitySlotSecondaryObjectGet @ 0x00471a50` read object pointers from `+0x18 + slot*4` and `+0x24 + slot*4`. `VelocitySlotVectorRead @ 0x00471c70` copies a slot vector from `+0x44 + slot*0xc`.

`EntityVelocitySteerBlendUpdate @ 0x00471a60` optionally copies a supplied vector to per-slot target coordinates at `+0x68 + slot*0xc`. When the slot has a primary object and delta exceeds `1e-5`, it compares that target to the object's current position, scales the current direction by `5/delta`, adds a normalized direction toward the target, renormalizes, clamps the vertical component to the record's `+0x30` bound, then updates the secondary and primary object poses. The constants and field layout are direct evidence; the conceptual meaning of the `5/delta` steering response is not named.

`EntityVelocitySlotDispatch @ 0x00471fc0` reads the state record's slot count at `+0xa4` and iterates each slot unless entity flag byte `+0x3ec` bit 0 is set, in which case it runs `VelocitySlotSteerDispatchAndSound @ 0x00471d20`; otherwise it runs `PoseOffsetVelocitySlotBlend @ 0x00471f00`. The dispatcher is called by the simulation queue flush path (Finding 247). `PoseOffsetVelocitySlotBlend` obtains the component object's orientation and position, scales the orientation vector by 10,000, adds the position, writes that target through the velocity-record helper, and applies the steering blend (Finding 256).

`VelocitySlotSteerDispatchAndSound @ 0x00471d20` first seeds/applies the slot blend, then requires the shared active-object predicate, global bit `0x400`, and a nonpositive slot value before tracing. It checks selection/callback state and visits at most two candidates. A candidate with an eligible slot record yields its type/configured range and speed (with 1.0 fallback); the routine calls `LaserSpatialSoundAndImpact @ 0x0046ffb0` from the candidate's position, applies `TypeMotionScaleApplyDispatch` to a returned entity, and caches that pointer at entity `+0x3c4`. When the first candidate path is used, it stores the slot value/vector and emits action feedback. Finding 256 documents the caller at `0x00471fec` and the named helper chain; the meanings of global bit `0x400` and cached field `+0x3c4` remain unresolved.

## Segment and entity collision queries

`EntityWorldCenterPositionRead @ 0x00471ca0` resolves the entity's scene object, reads its position, and subtracts half the entity field returned by `NestedFloatAtOffset74Get` from the vertical component. `EntityFlag100AndSharedEligibilityCheck @ 0x00471ce0` requires entity-record flag `0x100` and a successful shared eligibility check (`FUN_004385b0`), with its second argument depending on whether the entity kind is 4.

`RayHitCellDistanceMinimizeSweep @ 0x00471630` receives a ray/query record containing a segment, current nearest parameter, and output state. It maps both segment endpoints to terrain cells, clamps the cell coordinates to map bounds, orders the rectangle corners, and scans all cells in that box. For a candidate cell hit, it computes a normalized distance along the segment; when nearer than the current parameter it tightens that parameter and updates the hit/output fields. `SceneSegmentTraceNearestHit @ 0x00471860` initializes the query record, invokes the object callback `LAB_00471370` via `FUN_004377b0`, runs the cell sweep, restores the caller's range value, and returns the found object/result fields. Finding 258 records its additional callers from `RayHitScanAndEffectApply` and laser/segment tracing.

`ObjectPairRayHitCheck @ 0x004718d0` traces from one entity's world center toward the other's and returns true only when a hit is found and the returned object is not the target entity. `SeeThroughWallsRayCheck @ 0x00471960` queries the `SeeThroughWalls` config entry and returns false when `FUN_004790d0` returns nonzero; otherwise it traces the center-to-center segment through the terrain sweep and returns that result. `PlaceCommandEligibilityCheck @ 0x00404fc0` first requires `EntityCentersWithinObjectRadius` and rejects when this ray helper returns nonzero. `EntityType26CommandCompletionGate @ 0x0043c3e0` requires `EntityCentersWithinConfiguredRadius` and returns true only when `ObjectPairRayHitCheck` reports no intervening hit. These callers establish how the query results gate their respective operations; the config lookup result itself is not interpreted as simple key presence.

`InterpolatedZWithinBounds @ 0x00471330` computes `z = start.z + delta.z * t` and returns whether `param_4 - param_3 <= z <= param_4`; the parameter roles are literal from the body, while the caller-level meaning is not established by this helper.

`EntityCentersWithinConfiguredRadius @ 0x00472080` calls `EntityCanDoActivityClassify @ 0x0043c440`, which maps entity kinds 4, 5, and 7 to classes 1, 2, and 3 and returns zero for other kinds. A nonzero class selects the configured threshold through `FUN_0046f170`; the helper then compares the two world-center positions against that threshold using strict `<`. `EntityCentersWithinObjectRadius @ 0x00472130` uses the first entity's nested field at `+0xe4` as the strict distance threshold instead. `PlaceCommandEligibilityCheck @ 0x00404fc0` uses this object-radius predicate; Finding 357 identifies it as evidence for the collision-radius accessor.

## Limits and follow-up

The code establishes slot offsets/strides, kind selection, exact flag checks, query bounds, nearest-hit update, and caller-visible boolean conditions. It does not define all velocity slot fields, the semantics of global/entity flag bits, or every caller's interpretation of “hit” and “visible.” Existing findings already cover the projectile-impact, entity-radius, and simulation-dispatch slices, so this map does not create duplicate implementation tickets. A useful future slice would map the type-specific velocity slot layout to runtime entity examples and establish which caller consumes each visibility/obstruction result; the assigned functions alone do not settle those semantics.
