# 120 — Sound loading can fan one sample buffer out to two duplicates

`FUN_0047b6c0` creates a DirectSound buffer with `IDirectSound::CreateSoundBuffer` (vtable offset `+0x0c`). The `DSBUFFERDESC` fields observed in its setup are size `0x14`, flags `0x200f2`, byte length from the sound record at `+0x104`, and format pointer from `+0x11c`; the returned buffer is stored at `+0x120`.

The helper's second argument controls an additional branch. Ghidra's pseudocode does not recover that argument cleanly and renders the gate as a test of a zero-initialized local. The instruction at `0x47b72a` instead reads the second stack argument, and `TEST/JZ` at `0x47b738–0x47b73a` gates the branch. When nonzero, the code calls `IDirectSound::DuplicateSoundBuffer` (vtable offset `+0x14`) twice, storing the results at `+0x124` and `+0x128`. It clears the record field at `+0x12c` before this branch.

`FUN_0047b580` calls this helper with its own third argument, then calls `FUN_0047b790`. That loader locks the primary buffer, copies the sample bytes from the allocation at `+0x118`, unlocks it, and reads back current position and volume. DirectSound documents duplicate buffers as sharing the original buffer's sample memory, so creating the duplicates before copying the sample makes the loaded data available through all three buffer objects. Finding 133 establishes the three-buffer selection policy, and finding 134 traces the duplicate argument to the leading `*` on shipped `Samples` paths. The audible effect of the fan-out remains untested.

**Evidence.** REA/Ghidra 12.1.4, shipped `LegoRR.exe`, SHA-256 `c3d8ce23f1aa21814950c77e713ec176599506d4e71758cf1cf709525e581e0f`. Bundles: `docs/evidence/legorr-sound-buffer-duplication.bundle` and `docs/evidence/legorr-sound-buffer-fill.bundle`. Focused records: `ev_42a48d242a5c0f775c2ebfcbf3fe6538712d8722f03b1612835635c5ed8d561f` (creation, argument gate, and duplicate calls); `ev_308ac0d8588640ad0c956c15970f7b638dd121344666e24d6ebff1fd8efe8a66` (sample copy into locked buffer); `ev_1d6630a8e7c03dbe0d54889e6c448eecfc1bf8a7e74a22a9406839be85ab9d02` (caller sequence and third-argument forwarding). The shared-memory behavior is described by Microsoft's [`IDirectSound::DuplicateSoundBuffer` documentation](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/mt708944%28v%3Dvs.85%29).

**Limits.** Static analysis only; no DirectSound runtime was exercised. The duplicate-creation condition is supported by assembly because the decompiler omitted the second parameter from its signature. The flag value is recorded without assigning meanings to its individual bits. No claim is made about which game sounds request duplicates or how playback chooses among them.
