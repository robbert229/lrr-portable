# Finding 428 — Font and Text-Buffer Rendering

This map covers the 25 functions assigned by Issue #178. They form a shared path from font-atlas resources and target-device color conversion through formatted drawing and the ring-buffer text widgets used by menus, advisor messages, and other interface surfaces. Record field names remain provisional where the pseudocode only establishes offsets and operations.

## Font atlas and draw metrics

`FontResourceLoad` (`0x00479ee0`) loads a bitmap surface, acquires a font-resource record for it, retains the surface, and derives glyph metrics from its dimensions and pixel data. The code divides the atlas into 10 columns by 19 rows, scans each cell's pixel values to adjust its glyph advance, records the atlas metrics, and finalizes the resource. The exact pixel-mask interpretation and the complete record layout are not named. `ResourceNameCacheGetOrLoad` (`0x00410560`) lazily calls this loader for a resource key; `MenuBuild` (`0x004140c0`) reaches it through the cache (finding 393). A failed metric/data path releases the acquired record and surface.

`FontRecordCreate` (`0x0047e050`) acquires a 0x20-byte record from its own free list (growing the pool when empty), initializes the supplied fields and self-link, and converts its two color arguments through `FontDeviceColorConvert` (`0x0047e190`). The color converter unpacks RGB input, queries the target surface pixel format through its interface, shifts channel values into the reported masks, bounds the result to the pixel width, and releases the interface lock. The calls establish target-format conversion; they do not establish the user-facing meaning of the two color slots. `FontRecordAndSurfaceRelease` (`0x0047a550`) releases the surface/resource at field 0 and returns the font-atlas record to the free list. Finding 387 distinguishes this pool from the separate 0x20-byte font-record pool consumed by `FontRecordCreate`.

`BitmapFontGlyphDrawAndMeasure` (`0x0047a470`) maps supported byte values from space upward into the 10-by-19 atlas grid, optionally blits the glyph when its draw flag is set, and returns the glyph advance. `BitmapFontGlyphMeasureWidth` (`0x0047a520`) calls it with drawing disabled. `FontRecordCreate`'s separate color record and the atlas resource are therefore cooperating inputs to text rendering, but are not the same allocation family.

## Formatted text drawing

`FormattedTextDrawAndMeasure` (`0x0047a1e0`) first rewrites `%b` markers into an inline bitmap token form, formats the resulting template through `FormattedTextBufferBuild` (`0x0048e1e0`), and walks the output bytes. Newlines advance by the font's stored line-height field, tabs advance to the next tab stop, ordinary characters use `BitmapFontGlyphDrawAndMeasure`, and recognized inline bitmap handles are blitted while contributing their width and height. It returns the maximum line width and can write the line count to an output pointer. The meaning of the stored font metrics is inferred from these arithmetic uses.

The wrappers share this core with different modes: `FormattedTextFormatDraw` (`0x0047a150`) runs format/measure mode and can store the measured width through an optional pointer; `RewardTextDraw` (`0x0047a180`) and `FormattedTextDraw` (`0x0047a1b0`) enable drawing at the requested origin. Finding 232 maps the glyph and formatted-text behavior. The menu path queues `FormattedTextDraw` calls during its tick (finding 393), while scrolling and debug text use the width/draw wrappers described in finding 427.

`FormattedTextBufferBuild` initializes a string-backed `FILE` record and calls VC5 `__output` (`0x004909d0`) to expand the printf-style arguments, then terminates the output cursor or calls `__flsbuf` on overflow. The MSVC port now uses that runtime path directly while setting the stream's available byte count from its capacity argument; portable builds use bounded `vsnprintf`. Finding 397 traces the shared formatter and its wider set of supported specifiers. `%b` handling belongs to the text-draw wrapper's preprocessing; it is not a standard conversion in the shared formatter.

## Text widget storage and append path

`TextBufferCreate` (`0x004850f0`) allocates and zeroes a 0x830-byte widget record, copies its four-coordinate rectangle, stores its font-resource pointer, allocates the requested text capacity, records the capacity, and sets bit 2 in the flag word at `+0x82c`. `TextBufferDestroy` (`0x00485190`) frees the owned text allocation at `+0x14` and then the widget. `ObjectField10Get` (`0x004850e0`) reads the dword at `+0x10`; its exact type depends on the calling record. `FloatPairAtOffset4SetFromInts` (`0x004851b0`) stores two integer inputs as floats at `+4/+8`, and `FloatPairAtOffsetCSetFromUInts` (`0x004851d0`) stores two unsigned inputs as floats at `+0xc/+0x10`. `TextOutputField82CBit2SetClear` (`0x00485160`) toggles bit 2 at `+0x82c`; the broader meaning of this bit is not established by the setter itself.

`TextBufferAppendFormat` (`0x00485230`) and `FormattedTextAppendToRingBuffer` (`0x00485210`) are wrappers over `TextBufferAppendVFormat` (`0x00485250`). The V-format path expands the format into a temporary buffer, optionally skips through a requested number of BEL (`0x07`) markers, and appends remaining bytes at the cursor at `+0x41c` into the owned circular storage. When the cursor reaches the capacity at `+0x418`, it wraps to zero and sets bit 0 at `+0x82c`. This append path is used by the incident-message/advisor flow: `FUN_0045a590` forwards text to `TextBufferAppendVFormat`, and the message consumer resets, appends, scrolls, and draws the widget (finding 57).

`ObjectiveAdvisorTextCopy` (`0x00485300`) formats into a temporary buffer, copies the result into inline widget storage beginning at `+0x18`, sets the value at `+0x828` according to its second argument, and sets bit 1 at `+0x82c`. The objective/advisor worker sends parsed display text through this path (finding 94). The exact meanings of the `+0x828` state and flag bits 0/1 remain unresolved.

## Wrapping, display state, and reset

`TextBufferDrawWrapped` (`0x00485390`) derives its visible-line count from widget height and font line height. It scans the circular text from the read position, stops at BEL (`0x07`), treats LF (`0x0a`) as a line break, measures glyph advances, and records line starts when whitespace or width limits create a wrap. It draws the selected visible rows through `BitmapFontGlyphDrawAndMeasure` and can report the drawn height. When widget flag bit 1 is set, it delegates to `TextWrapMeasureAndDrawLines` (`0x00485710`), which measures and draws the inline text stored at `+0x18`, wraps on line breaks and the character-class whitespace predicate, and advances a timer/state field; when that timer expires it clears bit 1. The helper's exact animation/scrolling mode name is not established, but the dispatch and state update are observed. Finding 244 describes its two-pass measurement/draw flow.

`TextBufferReset` (`0x004859b0`) zeroes the owned ring storage and 256 dwords of inline widget state, clears the state value at `+0x820`, resets the write cursor at `+0x41c`, and clears bit 0 at `+0x82c`. It does not clear every flag in that word. `ObjectStatePairGet` (`0x00485a00`) returns values at `+0x820` and `+0x824` through output pointers; the surrounding code does not establish their user-facing labels.

The combined data flow is: producer text is formatted into either the ring buffer or inline storage; the widget tracks read/write position and state flags; the draw path measures glyphs, wraps rows to its rectangle, and draws glyph/bitmap cells from the shared atlas. This static flow links the objective/advisor and incident-message consumers to common drawing primitives, but does not prove runtime visibility for every submitted string.

## Unresolved questions

- Decode the font-atlas pixel mask and precise metrics stored at `+0xbe4/+0xbe8`, including the width extraction threshold.
- Trace ownership and release paths for the two font record pools and determine whether every resource-cache path balances retain/release operations.
- Map the widget flag word at `+0x82c`, inline state at `+0x820/+0x824/+0x828`, and read/write cursor fields to the higher-level scrolling and message-state APIs.
- Establish how `%b` bitmap handles are supplied and whether all callers keep those handles alive through the draw call.
