## Event and lifecycle ownership

`frontend_open_prepare` resets selection, quit and pending level, but not `load_slot` or `resume_level`; open clears submenu run flags (`src/game/frontend.cpp:2452`, `:2509`). Events are return values, not a persistent queue. Next items navigate to their configured MenuN, reset selection and return NONE (`:2907`). Escape in any nonroot submenu instead jumps directly to root; at pause root it closes and returns RESUME, at other roots closes, sets `fe.quit`, returns QUIT (`:3073`). Click/Enter activation and Escape are edge-driven in the callers; pause consumes the opening input, initializes the gate event to NONE every iteration, and after modal exit rearms pointer and rebases gameplay time (`src/gods98/frameloop.cpp:3858`, `:3927`, `:4005`). The gate callback passes through the event and sets an action flag for non-NONE (`:2078`).

## Save, load and reward callers

* Reward Save opens separate FE_MENU_SAVE, sets `save_action` (`frontend.cpp:2585`); a slot row stores its ID in `load_slot`, closes, returns SAVE (`:2836`). The gameplay save-modal caller handles only SAVE: set active slot, build checkpoint, write and mark `current_record`, update slot display (`frameloop.cpp:3790`, `:3807`). Configured image Back closes with NONE (`frontend.cpp:2867`); root Escape closes with QUIT and sets `fe.quit` (`:3073`), but this caller discards that event and returns one frame, so next frame leaves the modal and returns to reward. It does not set application quit in this path. Compare Back and Escape from the same reward state, including next click, save contents, and process survival; assert cancellation does not write a slot if paired evidence supports it. Reopening resets `fe.quit`.
* Main Load row emits LOAD irrespective of populated state (`frontend.cpp:2836`). `save_slot_state` returns false on absent/unreadable slot, and probes without creating the slot file, though it ensures the directory (`savegame.cpp:785`). Main caller on false chooses `LEGORRR_LEVEL` or `Level01` and still returns LOAD (`frameloop.cpp:3067`); application enters GAMEPLAY_START (`:4538`). On success it sets pending slot/record, game slot/current record, resolves record to campaign level or first campaign/Level01; gameplay preparation reads pending record (`:3071`, `:3593`). Empty-path code does not assign those fields; initial pending slot is -1 (`:3513`), so do not assume an empty selection loads a save. Compare an actually selectable empty slot and an occupied one from equivalent startup, capture screen, resulting level and slot changes; assert routing and no spurious writes only once established by paired evidence.
* Reward draw enables Save only for result 1 but draws Advance for all results (`mission.cpp:1162`); `mission_reward_zone` makes success Save and non-success Advance mutually exclusive (`:1239`). This is a definite draw/hit-test inconsistency for the success Advance rectangle (assuming nonoverlapping rectangles), not proof of a retail defect. Boundary rules also differ: drawing hover uses strict left/top bounds (`:1176`), hit testing includes them (`:1233`). There are two real frame paths: the modal reward tick dispatches `reward_zone_dispatch`, Save opens menu and consumes input; Advance calls `checkpoint_step` and sets transition stage 3 (`frameloop.cpp:345`), while the post-modal gameplay handler calls `mission_reward_advance` directly (`:4345`); default reward-screen callback also uses the same zone and stage (`mission.cpp:2159`). `mission_reward_click` is another public wrapper with checkpoint precondition (`:1269`); no source caller was found. Do not conflate modal stage transition with the later direct advance. On success and failure, separately click centers of each visible button during and after task reveal, then observe save modal, checkpoint, next level/campaign end, and input consumption. If paired evidence establishes an issue, regression assertions must exercise the real relevant caller phase and resulting lifecycle, not just a synthetic rectangle.
