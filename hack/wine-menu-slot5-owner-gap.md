# Occupied load slot: caller and progress seam

The paired slot-5 result in `wine-menu-parity-matrix.md` establishes that retail returns to the campaign map while candidate `a031…a0d6` starts Tutorial01 and restores record 0. The candidate log and ordinary actions are retained in `~/.local/share/lrr-devbox/menu-spacing-20261103-candidate-final/`; no code change or new runtime was made during this trace.

`fe_activate` emits `FE_EVT_LOAD_GAME` and the selected slot; `frameloop_main_menu_frame` reads the slot, maps the resume record to a level, and the application tick sends that event to `FRAMELOOP_PHASE_GAMEPLAY_START`. This explains the candidate result. A correct occupied-slot caller must remain in the frontend, retain the selected save and its progress, show the campaign map, and defer level and checkpoint loading until a mission selection. Merely opening submenu 1 would omit essential progress state.

The missing bridge is concrete. `save_slot_state` reads slot records; `save_menu_refresh` selects the slot and calls `sav_tree_load`, whose recovered walk sets bit 4 in packed menu blocks according to record flags and graph traversal. However, no production caller installs either `sav_menu_window_install` backing window; only tests install one. `frontend_sav_menu_list` builds a separate typed row snapshot, whose `open` field reflects authored config, and has no production consumer. The actual visible and selectable picker is `fe_graft_picker`'s static `NextLevel` chain; its `FeItem` has no unlock/progress state, and the hit/activation paths accept those rows without consulting the tree. Furthermore, the current record ↔ level mapping is explicitly a port stand-in (tutorials then campaign chain), whereas the recovered tree uses each node's registry index. Existing source therefore does not establish how selected-slot records map to the visible rows, nor the retail rule and current selection when the map opens.

Before an implementation can claim the requested contract, recover the packed SavMenuList row/registry-index and flag-to-draw/hit behavior and connect the selected slot's SavTreeLoad results to the actual picker, including branching LevelLinks rather than only NextLevel. A focused reference experiment should capture the same slot-5 campaign map's selected node, enabled/locked nodes and hover/activation, then compare a second legitimately progressed slot if available. It must preserve both runs and avoid creating or overwriting saves. Empty/invalid slot behavior remains unknown. A regression should exercise the real frontend/frame seam with occupied records and a branching graph, asserting selected slot and node state, no game-level/checkpoint call on slot selection, and a level start only after an enabled node is selected.

## Save-path correction and evidence qualification

The earlier claimed matched-slot divergence is invalid: retained reference journals show reads under `Data/Saves`, whereas candidate `a031…a0d6` read root `Saves`. The authenticated snapshot shows 33-record Data slots versus one-record root slots. Reference `SavReadSlot` passes `Saves\\N.sav` to `GameFileOpenDispatch`, which resolves it against the configured data root (`0x480220`); candidate typed `FILE` paths previously bypassed that resolver. The new runtime owner binds its typed save directory to `resource_path_resolve_against_base("Saves")` after resource startup; null or overlong resolution aborts startup. This keeps explicit test overrides and underlying save reader/format behavior intact.

A disposable fixture linked the actual resolver and savegame objects (with unrelated native resource compile workarounds in the fixture only). It verified a configured Data-root 33-record preview without byte/hash, size or mtime mutation; a mismatched or absent slot did not write/create; a distinct root `Saves/5.sav` sentinel remained unchanged; OSF and thumbnail paths used the same Data/Saves directory; an overlong resolved root was refused. See `~/.local/share/lrr-devbox/menu-load-fix-20261104/path-harness-result.log`, harness source and fixture object details. The picker/load behavior remains unverified on matched runtime data.
